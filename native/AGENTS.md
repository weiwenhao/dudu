This directory is the native SwiftUI iOS app. The parent repository also retains the previous Expo prototype for reference; Expo navigation and build rules do not apply to this native target.

- The minimum supported version is iOS 18. Build the project with `npm run native:build`. `native/project.yml` is the source for XcodeGen; do not hand-edit the generated project.
- Keep conversation, composer, voice, session switching, navigation, settings, and pairing in SwiftUI and native Apple frameworks. Embedded WKWebView pages may reuse DSH plugins, trace, context, team, and complex project tools. Do not move core interactions back into a web view or add React Native.
- Web content loads directly over HTTP or HTTPS under `/dsbot/ui/`, using a page-scoped HttpOnly cookie obtained by native pairing authentication at `/dsbot/web/open`. Documents, resources and page RPC/streams require this authentication. The legacy private scheme is retained only for simulator fixtures. Do not add anonymous pages, a general HTTP proxy, or unrestricted DSH RPC forwarding. Web pages must never receive pairing credentials.
- All native API calls and embedded pages use authenticated HTTP/HTTPS. Native live updates use HTTP long polling; do not add a WebSocket transport. Legacy WS/WSS pairing URLs may be normalized to HTTP/HTTPS only as an import migration. Never send pairing credentials in request URLs or logs.
- Preserve the app bundle identifier and signing team when updating an installed app, and keep old Keychain records until migration is durable.
- Keep decoding, Keychain I/O, image preparation, and diagnostics file writes away from the UI thread.
- "I tap a button and the app does not answer for a while" (owner, 2026-11-07) is read off the diagnostics, not guessed: `UserActionRecorder` logs every tap (`user.tap`: where on the screen, and how long the touch waited for the main thread, `elapsedMs`; state `late` from 250 ms) and every press and hold (`user.hold`), never what was tapped or typed (the keyboard's window is left alone); `UIResponsivenessMonitor` logs the main thread's stalls (`ui.main_thread_stall`); the requests to the computer log their time (`http.request.complete`). `npm run logs:pull` and `node scripts/device-actions.mjs <timeline.jsonl>` put them side by side: for each tap, the requests that started after it and how long the longest took, and whether the main thread stalled (`summary.json` has `actions.slowTaps`). The first reading of a pulled log (2026-11-07, 8359 records): no main-thread stall at all, and slow requests to the computer (`session.list` p90 2.2 s, max 17 s; `catalog.get` p90 4.7 s; `session.watch` max 17 s): the waits are the computer's answers, so a button that starts a request must show something within 200 ms (the rule above) rather than wait for the answer.

Do not list DSH features in the app; add a route for a DSH id in `host/native-navigation.mjs` instead. A screen the app draws itself is named by `open.native`; everything else opens as an embedded DSH page named by `open.web`. Fixture data for navigation is generated from the plugin's own routing (see `ReviewNavigation.swift`), never written by hand.

Keep observing the modal's parent after initial readiness, confirm the selected registry section before reporting ready, and hide the desktop root beneath DSH's settings portal so a failed market request cannot expose the home screen.
