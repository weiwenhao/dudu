## UI consistency: lesson recorded on 2026-11-01

The previous image-upload implementation connected selection, preview, and sending, but used generic controls without adequately comparing the attachment entry, tile styling, and removal interaction with DSH. Functional tests were treated as evidence that the UI was finished. The owner had to identify these inconsistencies and rewrite the conversation box. This was an implementation and verification mistake; the owner explicitly requires this lesson to apply to all future feature additions and changes.

- Before changing UI, read the relevant approved design and inspect the current implementation and comparable DSH controls. The owner's latest rewritten conversation box is the reference for subsequent changes there.
- Reuse established components, tokens, and interaction patterns. Match dimensions, spacing, corner radii, borders, colors, icon size and alignment, control placement, and hover, focus, disabled, and touch behavior. Using shadcn or Tailwind alone does not ensure design consistency.
- Extend the existing visual language when adding functionality. Changes to that language or to established interaction patterns need explicit owner direction; routine implementation that follows the existing design can proceed.
- Verify functionality and design alignment separately. Compare the rendered result with the reference when UI inspection is authorized. Respect the owner's explicit-permission rule for ego-browser.
- Report what was actually verified. Do not claim that the UI matches the design based only on code review or passing tests; identify any visual or interaction details that remain unchecked.
- Do not add explanatory subtitles or helper paragraphs by default. The owner requested a review of all existing secondary copy on 2026-11-02; keep its exact wording and disposition in `docs/secondary-copy-review.md`. Retain actual user content and operational data as content, not as invented UI explanations.
- A button draws a focus ring only while the person is moving with the Tab key (owner, 2026-11-08: a blue frame round the sessions icon and the pet, "很多地方都有"): after a click, Esc or Enter the page hands the focus back to the button that opened a menu or window, and the browser would call that `:focus-visible`. `ui/lib/tab-focus.js` marks the root `data-dudu-tabbing` from a Tab to the next click or Esc, and the `focus-visible` variant in `ui/styles.css` needs it (editable fields keep their ring always). Use the Tailwind `focus-visible:` classes, or put `:where(html[data-dudu-tabbing] *)` on the element in plain CSS (the build puts `.dudu` in front of the whole selector, so never write `html[...]` first); never a bare `:focus-visible` outline.

## Compatibility with released apps (owner, 2026-11-21)

The plugin installs as the newest version, but an iPhone app waits days for review and people keep the builds they have (owner: "我不希望改动一点功能，所有人的旧版本就用不了了"). So every change to the plugin must keep answering every phone app that is out there. Today that is the iPhone App Store build 143 (API v1; the Android app and the plugin of v0.1.0 were taken down, and nothing speaks `/dsbot` any more). Rules:

- **Only add.** Never remove, rename, retype or repurpose a method, a field, an enum value or a path that a released build uses. New fields are optional; an old app ignores what it does not know. Words and icons that the plugin sends (page names, rows, icon geometry) change for old apps too, which is fine.
- **A changed shape is opt-in.** An app declares itself on `POST /api/v1/connect`: `{ app: { platform, version, build }, capabilities: [...] }` (`host/native-client.mjs`; the plugin keeps it on the connection as `connection.client` and on the paired device, and hands it to the board and settings handlers as `context.client`). A phone that declares nothing is the baseline, build 143, and is answered exactly as before. Give a new shape only when `understands(client, 'name')`. A new kind of settings row or a new field a page needs must carry what an old app can draw (title, subtitle, `to`) or go only to apps that declared it.
- **Plugin first, app later.** Ship the plugin with the new behavior dormant, then release the app that declares the capability: iPhone review time then costs nothing. Every new app build must send the declaration (the iPhone and the Android app both do; since 2026-11-21 with `settings.rich`: the long-press menus and the drawn 状态 page of the settings, `host/native-settings.mjs`); add the capability name to it when the app learns the new shape. Since 2026-11-22 they also send `board.push`: the plugin puts one small `board.changed` event on the held `events` connection of such an app when what the board shows changed (a turn began or ended, a question or answer was recorded, something was read or marked unread, an issue or a pin changed; `host/native-board-changes.mjs`, wired in `host/dudu-plugin/index.mjs`, sent by `native-server.mjs` `broadcast`, coalesced to one per connection and no closer than 0.4 s), and the app reads the board again at once; its own timer is then only a safety net (iPhone 30 s once a push has been seen on that connection, Android about 25 s at the end of an idle poll). An app that did not declare it is sent nothing new (build 143 is answered as before). Since 2026-11-22 they also send `board.latest`: a chat row of such an app (`board.list { layout: 'chat' }`) is the newest message of either side, not only the agent's last finished answer, with the same fields (owner: "其他 APP 都会显示我发的消息", with no "你：" in front): when what the owner said last in the conversation (`home/latest.mjs` `mine`, for 嘟嘟 also its last `@` line, `home/group.mjs` `ownLine`) is newer than that answer, `preview` is it on one line and `receivedAt` is its time, so the row goes to the top of the list when the owner sends; `unread` and `readSeq` stay the answer's, and the owner's own message never lights the red dot (`ownMessages` in `home/chat-home.mjs`; the desktop list and Dudu's `home/list` always do it). An app that did not declare it keeps the agent's answer and its time, as before. Since 2026-11-22 the iPhone also sends `board.wake` (owner: 「通过通知唤醒，然后将消息写入，避免打开手机 app 后拉几秒消息」; iOS suspends an App within seconds of its leaving the screen, so only Apple can wake it): when what the board shows changed and such a phone has asked this computer for nothing for 45 s (`isLive` in `native-server.mjs`), the plugin sends it one silent push, with no alert, sound or number (`apns.mjs` kind `board`; `host/native-board-wake.mjs`, wired in `dudu-control.mjs` beside `board.changed`; at most one per phone every 3 minutes, and a change inside the gap goes at its end; what Apple answered is in `diagnostics/wake.jsonl`), and the app, woken for a few seconds, reads `board.list` once and writes it into its board cache (`BoardWake.swift`), which opening the app shows at once (`BoardModel.adoptNewerSnapshot`). A reply or a question that nobody has read goes to such a phone differently (owner, the same evening: 「弹通知也行」, as long as opening shows the messages at once): as a notice, an alert without a sound that shows the conversation's name and what it said and also wakes the app (`host/native-board-announce.mjs`, `apns.mjs` kind `announce`; at once whatever the gap, and it starts the gap), because Apple delivers an alert at once and holds back only the silent kind. The notice carries `mutable-content` as well, for the notification extension that the iPhone has since 2026-11-22 (`native/ios/DuduNotificationService`, the way Signal and Telegram do it; owner: 「那你也这么做吧」; declared as `notifications.service`, which the plugin does not branch on): iOS starts the extension before the notice is shown, also with the app swiped away, and the extension reads `board.list` and writes it as a `BoardWakeRecord` in the Keychain, which the app adopts when it comes to the front; the app is woken after it as well, which still works if the extension could not reach the computer. An app that did not declare it is sent nothing (build 143). Apple does not promise the silent pushes (no more than two or three an hour are asked for, none after the owner force-quits the app), so opening still reads the board as before. The iPhone's board is written and keyed by the phone's own id of the computer (`Computer.id`), never by the id the push names (`Computer.computerId`). The Android app needs no push and no plugin change for the same (owner, 2026-11-22: 「安卓也做」): while a collector's bell keeps its background service running, that service hears `board.changed` on the connection it holds, reads `board.list` and writes the app's board cache, which the app takes on coming back to the front (`DuduConnectionService.keepBoard`, `DuduViewModel.adoptWrittenBoard`). The layout of 嘟嘟's own settings pages is the apps' since 2026-11-21 (owner: "整个嘟嘟设置，包括打开里面的都可以写死，包括里面的条目，从 api 获取的是值，而不是布局"): a new app asks `settings.data { section, target? }` for the values of a page (the answers of the actions the page reads, cut down to the fields it uses: `READS` and `FIELDS` in `host/native-settings.mjs`, kept equal to the builders by a test) and draws the page itself; against a plugin that does not know the method it falls back to `settings.page`, and released apps keep `settings.page` / `settings.act` as they were. - **Freeze what each release needs.** `tests/fixtures/app-contract-ios-143.json` lists the requests build 143 makes, and `tests/fixtures/app-contract-ios-143-shapes.json` holds every key and type of the answers it decodes, recorded from the plugin of its own commit (`scripts/record-app-contract.mjs`, over `tests/support/app-contract-cases.mjs`); `tests/native-app-contract.test.ts` checks both against the plugin of today. - **Dropping support is a decision, not a refactor.** Old apps cannot be told to update, so a method or field goes only after `pairing` shows no device still on the build that needs it (`client` in the device list) and the owner has said so.

- **The apps draw their own screens; the API gives values.** A phone screen's structure (its pills, rows, cards, menus) is fixed in the app and is on the screen as soon as it opens; only what the structure holds or offers to choose from (a list of providers, workspaces, models, statuses) is read from the computer, in the background, and fills in when it is there (owner, 2026-11-24, on the new-task sheet that showed a spinner until `tasks.options` had come back: 「底部的菜单应该是原生写死的…API 应该只加载值而不是菜单」). Never hide a structure behind a request, and never send a layout; a control that needs a value which is not there yet waits, disabled, in its place. The plugin keeps answering the older apps as before (the compatibility rules above).

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Commands

Use `bunx` instead of `npx` if the project uses bun (`bun.lock` present).

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
npx expo start              # start the dev server
npx expo lint               # lint
npx tsc --noEmit            # typecheck
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
```

Run lint and typecheck before declaring any task done.

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.
Docs: https://docs.expo.dev/eas/index.md

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md
