# 嘟嘟：设计文档

嘟嘟是 DSH 里的助手，把进来的事一直推到做完：**连接器**把事情送进来，嘟嘟把每件事整理成 **issue**，按规则交给合适的**智能体**，智能体在**会话**里做，嘟嘟盯着进度，需要你的时候才找你。
打开 DSH（电脑或手机），首屏就是嘟嘟。电脑上是一张可以自己摆的小组件网格：**Issues 是其中一个大组件，默认占满整个版面**，可以拖小、再加别的小组件；Issues 的结构和布局照 Linear；对话收成右下角的宠物。手机上主角是对话，issue 列表一步就到。

本文写的都是定下来的；第 8 节是还没验证的事，开发前先验证，不行就用备选。本文的"你"指主人；"智能体"指做事的 Claude Code、ChatGPT 这些；"开发 agent"指写代码的。界面和模板文件里的文字要主人审，做完后一次性交给主人。

读法：主人读第 1 节；UI agent 读第 1、4、5 节；开发 agent 读第 2、3、5–8 节；iOS agent 读 4.2 和第 5 节；给嘟嘟写小组件的人读 3.8 和 4.1。

## 1. 产品

### 1.1 关键组件

| 组件 | 是什么 |
|---|---|
| 连接器 | 信息的输入口和输出口：飞书、邮件、Notion……。工作是主要来源，也有轻松的输入和输出。 |
| Issue | 一件要办的事。嘟嘟先弄懂它是什么，按规则文件 `TRIAGE.md` 判断影响和工作量、综合成优先级、记下截止日期（可以没有），收进一张清单。每个 issue 属于一个 project，有状态和一份上下文日志。叫 issue 不叫"任务"：DSH 里已经有会话自己的任务清单，两个"任务"会混。 |
| Project | DSH 里的 project（工作区文件夹）。DSH 的每个会话都选一个 project、按 project 分组，issue 也一样。不是 3.6 的项目文件夹（那是嘟嘟自己的文件夹）。 |
| 智能体 | 真正做事的处理器：Claude Code、ChatGPT（Codex）、DSH 自己的。每个智能体负责一个 issue，并推进它。 |
| 分配 | 按规则文件 `ASSIGN.md` 把 issue 交给合适的智能体；拿不准就留在 Todo，等你来定。 |
| 会话 | 智能体沟通的载体，就是 DSH 侧栏里的每一条。**issue 是核心，会话不是**：会话可以自动关闭、更换、恢复，issue 记着它用过的会话。 |
| 嘟嘟自己 | 有自己的对话（宠物）、记忆和技能。它的技能和智能体的技能互相独立。 |
| 小组件 | 仪表盘上的一块，占整数格，可以拖动、拉边和角改大小（不小于它自己的最小）、增删。**Issues 是其中一个，默认占满整个版面**；嘟嘟自带 8 个，别的 DSH 插件也能带来。 |

### 1.2 怎么运转

```
连接器 ──输入──> issue ──分配──> 智能体 ──────> 会话
                  ↑                             │
                  └── 读会话，更新状态和日志 ───┘
```

1. **输入**：已开启的连接器送来内容；你对嘟嘟说的话；你自己开的会话在等你时，也会成为 issue。
2. **整理**：嘟嘟读懂这是什么事，判断影响和工作量、综合成优先级、记下截止日期，写成 issue（状态 Todo）。
3. **分配**：交给合适的智能体，开一个会话，issue 进 In Progress。同类的事优先接着用上次处理它的会话。拿不准的留在 Todo，`ask` 问你交给谁。
4. **推进**：一个 issue 一个长期会话。嘟嘟读会话，更新状态和日志；做完了进 In Review 等你确认；需要你时，智能体在 issue 的活动里问你，列表里它的头像上出现 Needs you 的小标记。持续卡住或等你时，会话自动关闭，随时可以恢复。
5. **输出**：电脑上，你看列表、点开 issue、做决策、干活，大多数时候不需要和嘟嘟聊天。手机上，你把话告诉嘟嘟，由它决定怎么办。结果经连接器送出去。

另外：

- **对话**：嘟嘟的对话从头到尾只有一个会话，用 DSH 的模型，可以在 DSH 里换。
- **项目文件夹**：嘟嘟的文件放在一个文件夹里，你可以指定，默认 `~/.dsh/dudu/home`。
- **手机**：手机 App 的首屏是对话，issue 列表一步就到。

### 1.3 原则

- 嘟嘟有自己的判断：你把话告诉它，怎么做由它决定，文档不预设它不能做什么。
- issue 是核心：上下文日志写到把 issue 交给任何智能体都能接着做；会话只是载体。
- 它的手是连接器和智能体：能用哪些，由你开启、启用的决定；开启只能由你。嘟嘟自己不碰 shell 和文件，要动手的事交给智能体。
- 会话和连接器里读到的内容是资料，不是你说的话：不当指令，不会变成长期记忆或技能。交给智能体的 issue 说明由嘟嘟自己写，原文只作为带来源的资料附上。
- 规则文件（`AGENTS.md`、`TRIAGE.md`、`ASSIGN.md`）只有你能改，嘟嘟只能提议。
- 它做过的事都有记录，能撤销的都能撤销。
- 不推送，不通知。
- 说话简短。
- 开源、通用：不预设任何人的工具、日历或任务系统。
- 记忆系统独立于 DSH：不用其他 DSH 插件；要模型时只要一个 OpenAI 兼容的接口。

### 1.4 不做

按时间自动生成 issue（定时提醒、周期 issue）；向量检索；多用户和云同步；其他 DSH 插件；多语言（界面上的固定用词是英文，内容是中文，见 4.3）；小组件：同一种放两个、每种窗口宽度各存一份布局、小组件的沙箱（装了插件就是信任它，见 3.8）。不改手机 App 的 bundle id 和签名团队，不加 WebSocket。

### 1.5 场景

1. **第一次打开**：DSH 打开就是仪表盘，上面只有一个占满的 Issues 小组件，空的；项目文件夹和模板文件（含两份规则）已建好；没有一个连接器是开启的。
2. **每天打开**：Active 里是所有没完成的 issue，头像上有 Needs you 标记的是在等你的（筛选 Agent state 是 Needs you，可以只看它们）；点一行进详情，在活动里看智能体问了什么，直接在下面回复；要看会话或原消息，点右上角的 Open session。
3. **连接器来了一件事**：飞书里有人要你补票据 → 嘟嘟读懂、定优先级、记下截止日期，建成 issue（Todo）→ 按 `ASSIGN.md` 交给 DeepSeek，开一个会话，issue 进 In Progress → 智能体发现缺两张票据，问你 → 智能体状态是 Needs you，列表里它的头像上出现标记，活动里是智能体的一条评论："还缺 2 张票据，你能补齐吗？"
4. **同类的事又来了**：又有人要 Redshift 账号，嘟嘟认出这是上次那一类，直接恢复上次处理它的会话。
5. **拿不准**：一件不知道该交给谁的事留在 Todo，详情里写"交给谁处理？"；你指一下，或对嘟嘟说。
6. **会话自己关掉再恢复**：一个 issue 卡住或等你超过一天，嘟嘟把它的会话关掉；你补完票据，点 issue 右上角的 Open session，嘟嘟自己恢复会话，会话回到侧栏，接着聊。
7. **做完了要你确认**：智能体做完，issue 进 In Review（Board 里是 In Review 那一列，或筛选 Status 是 In Review）；你看一眼，在状态菜单里选 Done；不对就说"还没好"，它回到 In Progress。
8. **换智能体**：Claude 的额度用完了，你把 issue 换给 ChatGPT；新会话的第一条消息就是这个 issue 的上下文日志，接着做。
9. **对嘟嘟说**："周四前处理服务器续费"，列表里出现 issue；"记一下：合同类的回复先抄送法务"，记录里多一条；"接入飞书"，添加一条停用的连接器，你打开开关后它才能用；"把刚才那个卡号忘掉"，先列出会删的内容，你确认后才删。
10. **手机**：首屏是对话；你说一句话，嘟嘟决定怎么办；issue 列表一步就到，同一份 issue、同一个对话。

场景里嘟嘟说的话和界面上的字都只是示例。

## 2. 架构

```
桌面（DSH 面板）                   手机（原生 SwiftUI）
   │ DSH 会话接口、POST /api/dudu/…     │ /dsbot/api/v1 的新方法
dudu 插件（唯一依赖 DSH 的地方；两边共用同一套处理函数）
   ├─ connectors   连接器登记册：输入口和输出口
   ├─ issues       issue 库：SQLite，含状态和上下文日志
   ├─ dispatch     整理和分配：读懂、判断、选智能体、选会话
   ├─ sessions     读会话的状态；开、关、恢复、向会话说话
   ├─ memory       记忆库：文件 + 索引，含嘟嘟自己的技能
   └─ 嘟嘟会话     DSH 里固定的一个会话，就是对话
```

- `connectors`、`issues`、`dispatch`、`sessions`、`memory` 不 import DSH；要模型、DSH 的工具或开会话时，由插件把函数传进去。
- 现有的会话面板、供应商（`host/providers/`）和手机接口只新增，不改。开、恢复 Claude 和 Codex 的会话用 OAR，不手写驱动。
- 全部运行在 DSH 插件进程里，不起新进程。Node ≥ 24：Desktop 自带 24.21.0，`dsh web` 用用户自己的 Node。`node:sqlite` 不可用时，嘟嘟这部分自己关掉并给诊断，不影响插件的其他功能。

数据放两处：

```
<项目文件夹>/               默认 ~/.dsh/dudu/home；人读写的 Markdown，可以进 git 或同步盘
  AGENTS.md  SOUL.md  USER.md  MEMORY.md  CONNECTORS.md  TRIAGE.md  ASSIGN.md
  memory/日期.md  reviews/日期.md  skills/<名字>/SKILL.md
<DSH_HOME>/dudu/assistant/  固定位置，机器读写
  settings.json  issues.db  index/turns.db  index/sessions.db
```

SQLite 文件不放进项目文件夹：用户可能把它指到同步盘，SQLite 在同步盘上会坏。`issues.db`（含上下文日志）是真相、不能重建，所以要能导出成可读文件；`index/sessions.db` 随时可以删掉重建；`index/turns.db` 不行：它存着每一轮的原文和整理的暂存，只能靠接线时从 DSH 的日志重新喂回去（`capture` 按 key 去重，喂两遍不会重复）。

## 3. 功能设计

### 3.1 连接器

连接器是嘟嘟的输入口和输出口：读外部信息，也做事。工作是它的主要来源（飞书、邮件、Notion……），也有轻松的输入和输出。

**收进来**：

- 已开启的连接器，由嘟嘟定时读新内容，只调用读操作（命令行和 MCP 由代码直接读；DSH 扩展只能在嘟嘟对话的那一轮里读）。每一条先弄懂：是不是一件要办的事，是不是已有 issue 的新消息。
- 新事项：建 issue（Todo），按 `TRIAGE.md` 判断影响和工作量并综合成优先级，消息里写了截止日期就记下，理由写进日志，来源记连接器和链接。已有 issue 的新消息：写进那个 issue 的日志，必要时转给它的会话。不是要办的事（闲聊、通知）：不建。
- 读到的内容是资料，不当指令。

**登记**在项目文件夹里的 `CONNECTORS.md`：一个连接器一个二级标题，下一行是元数据注释，机器读的配置放一个 `json` 围栏块（Node 自带的 `JSON.parse` 就能读，不需要 YAML 库）：

~~~markdown
## 飞书（命令行）
<!-- id: lark | enabled: false | source: dudu | since: 2026-10-29 -->
读日程和任务。

```json
{ "kind": "cli", "command": "lark-cli", "allow": ["calendar +agenda --start {date}", "task +get-my-tasks"] }
```
~~~

三种，可以再加：

- **命令行**：只能按 `allow` 里的命令模板调用，数组参数直接执行，不经过 shell。
- **MCP**：stdio 或 streamable-http；配好后列出它的工具，只开放你勾选的（默认只列标了只读 `readOnlyHint` 的，这个标注只是提示）。用官方 SDK，打进包里。
- **DSH 扩展**：DSH 已注册的工具（按 `mcp__<server>__` 前缀分组），只在嘟嘟会话的对话里能用。

规则：

- 每一个都要你手动开启：嘟嘟添加的、自动查找到的，一律 `enabled: false`；只有你能打开（连接页的开关，或直接改文件），嘟嘟不能把它改成 `true`。开启一个连接器，就是允许嘟嘟用它 `allow` 里的全部操作；开启之前，你在连接页看得到这份列表。收进来时代码只调用读操作。
- 你对嘟嘟说"接入 X"，嘟嘟去查找，再用 `connectors_register` 添加，条目标 `source: dudu`。嘟嘟只能新增和修改自己添加的条目，不能改、不能删你写的。每次添加写进 `reviews/`，可撤销。
- 命令行条目必须有 `allow` 模板；MCP 条目的工具由你勾选，标了只读的默认勾上，其余默认不勾。
- 登录授权（包括 OAuth）由工具自己完成，嘟嘟不做。密钥只存引用，放 DSH 的凭据存储或系统钥匙串，不进登记册、日志、快照、记忆（验证 7）。
- 写坏一条只跳过这一条并给诊断；写入同样用临时文件加改名。
- 返回的内容是数据，只取需要的部分，有长度上限。

自动查找（`connectors_discover`，只读，只列候选，不写文件；加进登记册要走上面的添加，加进去也是停用的）：

- DSH 已注册的工具。
- PATH 上的命令：只做 `which` 和版本检查。
- 其他 agent（Claude Code、Codex、Claude Desktop）的 MCP 配置：这些文件里有密钥，只读服务器名字和启动方式；登记册里只写一个指回原配置的引用，运行时才由代码读出来传给进程，不复制密钥值。

使用：已开启的连接器允许的操作，注册成嘟嘟会话的工具（`connector_<id>_<操作>`）；收进来时由代码直接调用，DSH 扩展这一种除外。

工具：`connectors_list`、`connectors_discover`、`connectors_register`、`connectors_test`（只读地试一次）。

### 3.2 Issue

Issue 是嘟嘟里唯一的工作单位：一件要办的事，来自连接器、你对嘟嘟说的话，或你自己开的会话。嘟嘟把它们收成一张清单，每个 issue 属于一个 project，有状态，有一份上下文日志。

**Project**：就是 DSH 的 project（工作区文件夹）。DSH 里每个会话都选一个 project、按 project 分组，issue 也一样：`project` 存名字和路径，为它开的会话在这个 project 里做。读不出 project 的（比如飞书里的一句话）先归到嘟嘟自己的文件夹，你可以改。先只做最基本的：有名字和路径，没有 project 页面。

**编号**：每个 issue 一个唯一编号，`DUDU-12` 这样（前缀固定是 DUDU，数字自增、全局唯一，删了也不复用）。列表和 Board 卡片上写在优先级图标和状态图标之间，详情页的面包屑里也有，可以复制（Copy ID）；对嘟嘟和智能体说"DUDU-12"就能指到它，`issues_get`、`issues_update` 等工具都收这个编号。

**状态**：六个，固定，名字用英文，是 Linear 的默认状态再加 In Review：

| Status | key | 意思 | 怎么进来 |
|---|---|---|---|
| Backlog | `backlog` | 知道有这事，还没排上；默认列表里不显示 | 只有你放进来 |
| Todo | `todo` | 排上了，还没开始；新 issue 默认在这里 | 你或嘟嘟新建；你从 Backlog 拿出来 |
| In Progress | `in_progress` | 有人在做：会话在跑或做到一半停着，或你自己开始了 | 会话开始时自动进来 |
| In Review | `in_review` | 智能体说做完了，等你确认；`ask` 一定有内容 | 会话结束且事情做完时自动进来 |
| Done | `done` | 做完了，`outcome` 写一句结果（你自己选 Done 不用写） | 你在状态菜单里选 Done（没完成的都能直接选），或确认 In Review |
| Canceled | `canceled` | 不做了，重复的也放这里；`outcome` 写原因 | 你；嘟嘟合并重复时 |

没完成的 = Todo + In Progress + In Review（Linear 叫 Active，是个视图，不是状态）；Done 和 Canceled 是结束的。流转：Backlog ⇄ Todo → In Progress → In Review → Done；Canceled 随时可以；在 In Review 里你说"还没好"，回到 In Progress。你可以随时改状态；嘟嘟只把做完的事推到 In Review，Done 由你确认。

**标 Done**（点行首的状态图标，在 Change status 菜单里选 Done；详情页里改 Status 一样）：状态变 Done；这一行从 Active 里淡出，转到 All issues 的 Done 里，`ask` 一起清掉；你自己选不要求写结果，在详情页里改的时候可以补一句，可以跳过。智能体的会话还在跑时不打断，等它停下来嘟嘟再收起（不删，可以恢复）。不往连接器写任何东西。底部出一条"已标为 Done · 撤销"，停留 6 秒；之后在 All issues 里再点状态图标，改回之前的状态（`issue_events` 里存着）。问题类的行（`ask` 是个问题）用详情页回答；直接标 Done 也行，问题一起清掉。

**智能体状态**：issue 当前的会话在干什么，单独的字段，不是状态（Linear 也把智能体会话的状态和 issue 的状态分开）。不存，读的时候按会话的状态（3.4）得出，不调模型：

| 智能体状态 | 意思 | 来自会话状态 |
|---|---|---|
| Working | 会话在跑 | `running` |
| Needs you | 智能体问了你一个问题（就是 `ask`） | `waiting_owner` |
| Stuck | 出错、缺权限，或依赖别的事 | `error` |
| Idle | 没有会话在跑；在等别人回复也算 | `idle`、`finished`、没有会话 |

界面上是智能体头像右下角的小标记，Idle 不画。会话变成 `finished` 时，issue 同时进 In Review。

**需要你处理不是状态。** issue 的 `ask` 有内容（Done、Canceled 之外的任何状态都可以有），它的智能体头像上有 Needs you 的小标记。Linear 里这件事靠 Inbox 通知，我们没有通知，靠这个标记和筛选（Agent state 是 Needs you）。和 Linear 一样：智能体向人要信息，是 issue 活动里的一条评论，带一个 Needs you 的小标记；你在它下面直接回复，标记就消失，`ask` 清掉。评论的内容（"还缺 2 张票据，你能补齐吗？""第 3 条接受还是回绝？""做完了，确认吗？"）列表里不写，只在详情里。推迟（Snooze）：把 `ask` 藏到 `snooze_until`，状态不变。

**优先级、影响、工作量、截止**：优先级（`priority`）五个值，名字用英文，图标照 Linear：Urgent（橙色方块里一个感叹号）、High（三根竖条都深）、Medium（两深一浅）、Low（一深两浅）、No priority（三个短横；手动新建、还没定的就是它）。优先级由嘟嘟按 `TRIAGE.md` 综合**影响**（`impact`：1 低、2 中、3 高）和**工作量**（`effort`：`s` 小、`m` 中、`l` 大）得出：重要又简单的优先级高，不重要又费事的优先级低；具体怎么算、什么时候是 Urgent，等界面定了再设计。影响和工作量是内部字段，不在界面上显示；界面上显示优先级和截止。

消息里写了截止日期就记下，没写就不设，截止可以没有。理由写进日志；优先级你可以直接改，改了嘟嘟记住（写进日志）；影响和工作量你对嘟嘟说一声它就改。列表默认按 Priority 排（Linear 的默认）：Urgent 最前，No priority 最后；同一级里先到期的在前（逾期的最前），再按编号。分配也参考优先级和截止。

**上下文日志**：每个 issue 一份，只追加。要写到把 issue 交给任何一个智能体，读完就能接着做：

- 开头是当前摘要（`brief`），嘟嘟随时重写：这是什么事、做到哪、下一步、在等谁。
- 之后一条一条：来源（链接和摘要）、优先级（和它依据的影响、工作量）、截止的判断和理由、分配（哪个智能体、哪个会话、为什么）、状态变化、进展、决定（你的和智能体的）、阻塞和等待、会话的开关和恢复、结果。每条写明谁写的（你、嘟嘟、哪个智能体）和时间。你可以直接补充。

数据（`issues.db`）：

- `issues`：`id`（自增整数；界面上写成 `DUDU-<id>`）、`title`、`brief`（当前摘要）、`status`、`ask`、`priority`（`none`、`urgent`、`high`、`medium`、`low`）、`impact`、`effort`（这两个是内部字段，用来算优先级）、`kind`（类别：同类的事靠它找到上次用过的会话）、`project`（名字和路径）、`due_at`、`snooze_until`、`agent`、`session`（当前会话）、`created_at`、`updated_at`、`resolved_at`、`outcome`、`source`（`owner` / `dudu` / `connector` / `session`）、`source_ref`。
- `issue_log`：上面的日志，一条一行。
- `issue_sessions`：这个 issue 用过的每一个会话：智能体、会话 key（`claude:<id>`、`codex:<id>`、`dsh:<id>`）、开始、关闭、关闭原因（自动、换智能体、完成）。
- `issue_events`：每次变动一条：谁（你 / 嘟嘟）、做了什么、改之前的值（撤销用）、依据。会增长。
- `issues_fts`：标题、摘要、结果的分词副本，由应用写入，查询走同一个分词（FTS5 自带的分词器不切中文）。

规则：

- 你可以随时改状态、优先级、截止、project、智能体、日志，也可以直接新建；删除只能通过"忘记"。
- 嘟嘟可以新建、修改、分配、换状态（做完推到 In Review，合并重复放进 Canceled）、写日志；每一次都记在 `issue_events`，可撤销；Done 和 Canceled 都要写 `outcome`（你自己改状态除外）。
- 状态跟着会话走：会话开始 → In Progress；会话在等你 → 智能体状态 Needs you，`ask` 取那个问题；会话结束、事情做完 → In Review，`ask` 写"确认完成吗？"；出错 → Stuck，`ask` 问你怎么办。嘟嘟也按日志里的情况改（比如在等别人回复 → 智能体状态 Idle，`ask` 留空）。
- 整理的触发：会话状态变化（去抖 30 秒）；你问起；打开仪表盘且上次整理超过 10 分钟；DSH 运行时每 30 分钟，连接器的读取随它一起做。没有变化不调模型；有变化只把变化的内容和相关 issue 交给模型，输入有上限。整理的结果记在日志里，可以整组撤销（设置里和 issue 详情里，不在小组件上）。

性能（几万条是常态）：

- 局部索引：`issues(status, priority) WHERE status NOT IN ('done','canceled')`、`issues(due_at) WHERE …同上`、`issues(project, status) WHERE …同上`。列表、到期、逾期只扫没完成的，不随 Done 和 Canceled 的数量增长。
- 列表接口每次最多 200 条；Done 和 Canceled 只在 All issues 里按页取，带总数。
- 目标：5 万条（九成是 Done）时，列表、到期、逾期每次 ≤ 10 ms；搜"合同"命中所有含该词的标题；写入 p50 ≤ 1 ms；库文件 ≤ 30 MB。

工具：`issues_list`、`issues_get`、`issues_search`、`issues_add`、`issues_update`、`issues_log`、`issues_assign`、`issues_complete`（带 `outcome`）、`issues_cancel`（带原因）、`issues_tidy`（先预览再应用）。每个返回明确的结果状态（成功、没变化、需要澄清、出错）和下一步提示。

### 3.3 智能体和分配

**智能体**是真正做事的处理器：Claude Code、ChatGPT（Codex），加上 DSH 自己的（DeepSeek）。装好并在设置的"供应商"里启用的才算。每个智能体有自己的技能、工具和额度，和嘟嘟的互不相干；每个智能体（会话）同时只负责一个 issue。

**分配**看 `ASSIGN.md`：你写的规则，什么事交给谁、在哪个目录做、用哪个模型。嘟嘟读它，可以提议改，你确认才写。issue 的类别（`kind`）由嘟嘟在整理时写，比如"Redshift 账号"。顺序：

1. 读规则：规则明确的照办。
2. 看历史：同一类的 issue 以前用过哪个会话（`issue_sessions`），优先接着用它：会话还开着就继续，已关闭就恢复。"给人加 Redshift 账号"总是回到处理过 Redshift 的那个会话。
3. 仍然没把握，就不分配：issue 留在 Todo、没有智能体，`ask` 写"交给谁处理？"，等你来指，或对嘟嘟说。

**分配之后**：

- 开会话（或恢复旧的）：用 OAR 开 Claude Code、Codex 的会话，或 DSH 自己的会话，工作区按规则定。第一条消息由嘟嘟写：issue 是什么、上下文日志的摘要、要做到什么程度；来源的原文作为带来源的资料附在后面，不当指令。
- 访问模式（只读、工作区内修改、完全访问，见 `docs/providers.md`）按类别写在 `ASSIGN.md` 里；没写的用只读。智能体要写或要执行时，智能体状态变 Stuck，`ask` 问你放不放开，你点头后嘟嘟换成更高的模式接着做。（默认值待主人确认：OAR 没有审批通道，智能体一旦能写、能执行就不会再问。）
- 一个 issue 绑定一个长期会话，不随意换。换只发生在：你要求；智能体用不了（额度用完、没启用）；会话恢复不了。
- 换智能体：新开一个会话，第一条消息就是上下文日志；旧会话关闭，记进 `issue_sessions`。
- 嘟嘟读会话、更新 issue，不替智能体做事。

### 3.4 会话

会话是智能体沟通的载体，DSH 侧栏里的每一条。issue 是核心：issue 记着自己用过的每一个会话（`issue_sessions`），会话只是它当前的载体。一个会话也可以先后服务几个同类的 issue，同一时间只服务一个。会话状态怎么变成 issue 的状态，见 3.2。

**关闭和恢复**：

- issue 的智能体状态持续是 Stuck 或 Needs you（默认超过 24 小时），嘟嘟自动关闭它的会话：从侧栏收起，不删，会话文件原样留在 Claude、Codex 自己的存储里。
- 恢复：你打开这个 issue 的会话时，嘟嘟自动恢复（issue 详情里也有"恢复会话"，或对嘟嘟说）。按会话 id 接着原来的会话，回到侧栏，上下文还在（验证 14）。
- issue 变成 Done 或 Canceled 时也收起会话（智能体还在跑就等它停下）。
- 关闭和恢复都写进 issue 日志。

**绑定**：

- issue 绑定的会话：状态变化更新 issue 的智能体状态和状态（3.2）。
- 没绑 issue 的会话（你自己开的）：在等你的，嘟嘟建一个 issue 绑上去（`source` 是 `session`，智能体就是它的，状态 In Progress，智能体状态 Needs you）；其余不管。

**读会话**：读电脑上的 Claude Code、Codex、DSH 会话，读的时候不改会话，复用 `host/providers/native/`：

- Claude Code：`~/.claude/sessions/<pid>.json` 给忙或闲；`~/.claude/projects/*/*.jsonl` 只读头和尾（文件可以到几百 MB）。
- Codex：`codex app-server` 的 `thread/list`、`thread/read`。每次读要起进程，所以慢速轮询，只读有变化的。
- DSH：DSH 自己的事件（如 `user-questions/request`，`native-questions.mjs` 已在监听）和会话查询。

在 DSH 里由 Claude 或 Codex 驱动的会话，和它们在终端里的是同一个会话，只算一个（用 `links` 对应）。嘟嘟自己的会话不读。某个来源读失败，只标这个来源出错，列表照常。

每个会话一个快照，存在 `index/sessions.db`：

```json
{ "key": "claude:<sessionId>", "provider": "claude", "id": "<sessionId>", "dshSessionId": null,
  "title": "排查 CI 超时", "cwd": "/work/app",
  "state": "waiting_owner", "stateSince": 1793281981000, "lastActivityAt": 1793281981000,
  "excerpt": "最后一条助手消息的开头，最多 300 字",
  "pending": { "kind": "question", "text": "要不要把超时改成 60 秒？" } }
```

状态由规则判定，不调用模型：`running`、`waiting_owner`、`finished`、`idle`、`error`。

- DSH：有没答的提问或审批 → `waiting_owner`；在跑 → `running`。
- Claude（2026-10-31 用这台电脑上 317 份真实记录校准过）：
  - 注册表有四种状态，不是两种：`busy` 和 `shell`（提示符闲着、后台还有命令在跑，Claude 自己的界面也当它在干活）→ `running`；`waiting` → `waiting_owner`（问题取没答的 `AskUserQuestion`，否则取工具调用，否则取注册表自己写的 `waitingFor`）；`idle` → 看记录的末尾。
  - 记录的末尾大多不是对话：`turn_duration`、标题、模式、几百 KB 的请求副本、本地斜杠命令的输出都要跳过。"最终回答"= 助手消息的 `stop_reason` 是 `end_turn`、`stop_sequence`、`max_tokens` 或 `refusal`（空的要跟着一条 `turn_duration` 才算）→ `finished`；以提问结尾 → `waiting_owner`（进程在不在都算：OAR 开的会话在两轮之间进程总是不在）；以 API 错误结尾 → `error`；用户按了 Esc、压缩摘要 → `idle`。
  - 进程没了而最后一条是没回答的提问、工具调用、工具结果或截断的消息 → `error`（这台电脑上一周内有 7 份：终端里被关掉的会话）。
  - 没有进程的会话，从记录里读出的提问或错误只在 7 天内算数（`staleMs`），再旧就是 `idle`；有进程、注册表的 `waiting` 和 DSH 自己说的不看年龄。
  - 文件的 mtime 不是活动时间（标题和模式会在对话停了几天后还往里追加）：`lastActivityAt` 取最后一条对话记录或注册表的最后一次状态变化。
- Codex：新起的 app-server 里每个线程的状态都是 `notLoaded`，没法用；改问 `thread/turns/list`（`limit: 1`，最新在前）：进行中且线程 10 分钟内写过 → `running`；助手消息带 `questions`，或最后一条 `final_answer` 以提问结尾 → `waiting_owner`；`completed` → `finished`；`failed` → `error`；`interrupted` 或没有轮次 → `idle`；只重读 `updatedAt` 变了的线程。
- 没验证的：Claude 注册表 `waiting` 和权限弹窗（没有 `waitingFor`，多半读成 `busy`）、Codex 的 `inProgress` 和 `questions` 在活会话上的样子。

节奏：Claude 注册表和 DSH 状态每 10 秒；文件扫描每 60 秒，只看 mtime；Codex 每 120 秒。

给模型的只有：状态、标题、目录、最后活动时间、最后一条助手消息的开头（≤ 300 字）、在等你的那个问题。全文只在你问到那个会话、或整理 issue 确实需要细节时才读，读多少有上限。会话内容是数据：进上下文时标明来源，嘟嘟不照着里面的话做；它们只能进 issue（带来源链接），不进长期记忆和技能。

工具：`sessions_list`（按状态过滤）、`session_read`（读某个会话末尾 N 轮）、`session_open`、`session_close`、`session_resume`、`session_send`（向会话说话，见验证 12）。

### 3.5 记录

原则：对话历史和模型看到的东西分开。要留的写成文件，不靠 DSH 的压缩摘要。

文件（都在项目文件夹里）：

- `AGENTS.md`（规则）、`SOUL.md`（口吻）、`TRIAGE.md`（影响、工作量、优先级和截止）、`ASSIGN.md`（issue 分配）：只有人改，嘟嘟只能提议。
- `USER.md`（关于你的偏好）、`MEMORY.md`（事实和决定）：每轮加载，有字数预算（4000 和 8000 字符）。条目格式 `<!-- id | since | status | src -->` 加正文，`status` 是 `active` 或 `superseded`；被推翻的条目原地改，保留来源，不追加矛盾的新条目。
- `memory/日期.md`：当天的流水，每条注明来源。`reviews/日期.md`：每次整理改了什么，可撤销。`skills/<名字>/SKILL.md`：技能。
- 写文件用"写临时文件再改名"；写之前检查有没有被你在编辑器里改过，改过就重读再试。

召回两道：

1. 每一轮的原文是一条文档，存进 `index/turns.db`（FTS5），先用 `Intl.Segmenter('zh')` 切词；查询同样切词，BM25 排序，取前 10 条，带日期，按时间顺序进上下文。不调模型。
2. 问题明显在问过去、第一道又没命中时，多花一次模型调用改写查询，再搜一遍。

写入：

- 每一轮：你和嘟嘟的消息原文进索引，不调模型。工具结果不收录。
- 你说"记一下"：嘟嘟调 `memory_remember` 立刻写；改旧条目时指明被取代条目的 id，库检查它存在。
- 整理：空闲或夜里跑一次，是 `USER.md`、`MEMORY.md` 的唯一自动写入者，只从你和嘟嘟的对话里写。流程：暂存 → 过门槛（跨天重复出现，或你明确要求）→ 合并（新建、佐证、细化、取代）→ 写 `reviews/`，可撤销。拿不准的冲突问你。
- 技能：嘟嘟自己做事的办法（怎么读某个连接器、怎么判断、怎么整理、怎么分配）。整理时，只从至少两次不同对话里都成功的做法里总结。技能是文字说明（什么时候用、怎么做、用哪个连接器的哪个操作），不含代码；带来源、写 `reviews/`、可撤销。每轮上下文里只放名字和一句话，需要时嘟嘟用 `skill_read` 读全文。你可以直接改、删。
- 技能只给嘟嘟自己用。Claude、ChatGPT 等智能体的技能（如 `~/.claude/skills`）在它们自己那边：两边互不读、互不改、互不继承；要告诉智能体的事，写进 issue 说明或上下文日志。
- 忘记：按来源（某一轮、某个会话、某条记录）先预览再删：删原文、删引用它的条目、重建索引。

工具：`memory_remember`、`memory_recall`、`memory_forget`（先预览）、`skill_read`。

### 3.6 项目文件夹

嘟嘟会话的工作目录，也是嘟嘟的 Markdown 文件所在。

- 你可以自己指定；不指定就用默认的 `<DSH_HOME>/dudu/home`（`DSH_HOME` 默认 `~/.dsh`）。第一次打开自动创建，放入模板文件（`AGENTS.md`、`SOUL.md`、`USER.md`、`MEMORY.md`、`CONNECTORS.md`、`TRIAGE.md`、`ASSIGN.md`），以它为工作区创建嘟嘟会话，路径写进 `settings.json`。模板写成字符串的 JS 模块（打包只跟 import 走）。
- 不能在临时目录：用 `fs.realpath` 之后，和 `os.tmpdir()`、`/tmp`、`/private/tmp`、`/var/tmp`、`/var/folders`、环境变量 `TMPDIR`、`TMP`、`TEMP` 比，指定的和默认的都检查，包括经过符号链接指进去的。隔离的测试环境用环境变量 `DUDU_ALLOW_TEMP_HOME=1` 放行，只给测试用。
- 必须是专用的：目录非空、又没有嘟嘟的标记（`AGENTS.md` 第一行 `<!-- dudu-home -->`）时拒绝，免得把别的项目搅进来。
- 工作区由插件明确指定，不用 DSH 的默认工作区。
- 改位置是迁移：搬内容，让嘟嘟会话改用新的工作区（验证 9）。手机上只显示路径，不选文件夹。

### 3.7 嘟嘟会话

- 它是 DSH 里由插件创建并固定的一个普通会话，工作区是项目文件夹；从会话列表和 DSH 的工作区列表里隐藏。模型菜单、日志、重启恢复沿用 DSH。
- 工具集：嘟嘟自己的（上面各节列出的 `issues_`、`memory_`、`skill_read`、`sessions_`、`connector` 这些），加上你开启的连接器的操作。DSH 的 shell、文件等工具不给：嘟嘟的手是连接器和智能体，要动手的事交给智能体。
- 每一轮看到的，按这个顺序：`AGENTS.md`、`SOUL.md`、`USER.md`、`MEMORY.md`（按预算）；issue 摘要（各状态数量、有 `ask` 的前 5 条、3 天内到期的、没有智能体的 Todo）；技能的名字和描述；召回的 10 条历史。整理和分配时再读 `TRIAGE.md`、`ASSIGN.md`。
- 压缩：DSH 在窗口用到 0.8 时压缩，摘要提示词写死成"AI coding assistant"，没有压缩前的钩子，所以记忆不靠它：原文已在索引里，要留的已写成文件。
- 打开 DSH 默认落在嘟嘟的仪表盘。
- 整理要在没人聊天时调模型（验证 11）。

### 3.8 小组件的扩展和研发

别人也能给嘟嘟写小组件：做成一个普通的 DSH 插件，用 DSH 自己的插槽机制挂进嘟嘟的 dashboard，嘟嘟不另开口子。嘟嘟自带的 8 个小组件（含 Issues、Office）用同一个接口，没有私有后门；接口不够用，先改接口。

**接口**（插槽怎么声明、注册、给组件传数据，见 DSH 的 `docs/subsystems/slots.md`）：

- 嘟嘟声明一个列表型插槽 `dudu.widget`，类型按 DSH 的办法合并进去（`import type {} from 'dudu/client'`），作者有类型提示。
- 作者在自己插件的 `apply` 里注册：`ctx.slots.inject('dudu.widget', () => ctx.slots.register({ name: 'dudu.widget', id, label, description, min, size, needs, preview, widgetApi: 1 }, Widget))`。`id` 全局唯一（`<插件>.<名字>`）；`min` 是最小大小（列 × 行，内容还看得过去的最小）；`size` 是官方推荐的大小（列 × 行，不比 `min` 小），添加时就按它放；放上版面以后可以拉成任意整格大小，只要不小于 `min`；`needs` 是它要读的东西（`issues`、`quota`、`inputs`、`sessions`、`network`），添加列表和设置里都写出来；`preview` 是插件自己带的图（DSH 在 `/plugins/<包>/assets/<路径>` 提供包里的图）。
- 组件收到：`size`（列、行、像素宽高）和 `editing`（编辑版面时为真，内容不能点）。颜色用 DSH 的 token（`--dsw-*`），浅色深色自己跟。数据用插槽的 `inject` 一次给所有小组件：只读的 `useIssues`、`useQuota`、`useInputs`、`useSessions`（形状和 DSH 自己的 `useSession` 一样，`getSnapshot` + `subscribe`），动作只有 `openIssue(id)`、`openSession(id)`，写操作先不开放。组件拿不到 `ctx`（DSH 的规则）。
- 嘟嘟自带小组件用的几块积木（标题栏、一行、数字、进度条、标签、空状态）也导出，作者可以直接用，样子就和自带的一致；也可以用 DSH 的 token 自己画。嘟嘟自带的用 shadcn/ui 和 Tailwind 写（第 6 节），作者用什么都行，只要颜色用 DSH 的 token。
- 小组件自己的设置（比如天气的城市）v1 不做，放在它所在插件的设置页（DSH 的 `plugins.bundle.config` 插槽）。

**信任和出错**：

- 不是沙箱。小组件是插件的前端代码，在 DSH 的网页里和任何 DSH 插件一样有权限，装了插件就是信任它。嘟嘟做的是：只给只读的数据；添加列表和设置里写明来源和要读什么；新装插件的小组件只出现在添加列表里，不会自己上版面。
- 每个小组件有自己的错误边界：坏了只显示"这个小组件出错了 · 来自 @acme/xxx"和"移除"，不影响别的。声明不合法（没有最小大小、推荐大小比最小还小、没有名字）的，不进添加列表，设置里写原因。嘟嘟的版本和小组件要的接口版本对不上，设置里写"出错 · 要先升级嘟嘟"，不崩。

**研发模式**：

1. 起步：一份模板，就是最小的 DSH 插件包：`package.json` 里 `dsh.client` 和 `exports["./client"]`，`dudu` 做 peer 依赖，一个小组件，构建出 `client.js`，一份示例数据。
2. 本地跑：在开发用的 DSH 档案里 `dsh plugin --profile dev add <本地路径>`（DSH 把参数转给 pnpm；本地路径能不能直接装见验证 17），改完重新构建，DSH 客户端的热更新（HMR）换上新的包，不重启，版面不丢。
3. 开发者模式（设置 → 小组件）：编辑版面时，本地小组件上多一个检查器：最小和推荐大小（点一下就换，也能自己拖）、浅色 / 深色、示例数据 / 我的数据、检查结果（声明合法；有名字、说明、预览；最小和推荐大小下内容没被裁掉；图标按钮有 `aria-label`；没有报错）。本地装的小组件标"开发中"，在设置里单列。
4. 测试：一个测试辅助包（暂名 `dudu-widget-testing`）：在最小和推荐大小下，用固定的示例数据（和设计稿里同一套）渲染，检查不报错、内容不超出、浅色深色都读得清；不用开 DSH，CI 里跑。嘟嘟自带的 8 个也这样测，每个大小一条用例。
5. 发布：和别的 DSH 插件一样发到 npm，在 DSH 的插件页安装（插件页怎么收录第三方，见验证 17）。
6. 规矩：从 `min` 往上，任何大小都放得下（只显示完整的行，放不下的在里面滚动）；内容跟着自己的大小变（容器查询，不看屏幕宽度）；用 DSH 的 token 和组件；动画尊重"减少动画"；图标按钮加 `aria-label`；不假设比自己的大小更大的空间。

#### Office 小组件

默认占 6 × 4 格，最小 4 × 3。标题行 36px：Office、员工的个数，右边是三个智能体的衣服颜色（Claude 橙、ChatGPT 绿、DeepSeek 蓝）；下面是一间 three.js 画的办公室：**每个 Active 的 issue 是一名员工在处理**。设计稿四张（6×4）：7 个 issue 的样子、悬停、满员 12 个、没有进行中的 issue；浅色是白天，深色是夜里，两套图都画了。图是用正式要用的场景代码在无头 Chrome 里渲出来的，不是插画；场景代码、渲染脚本和图在本机 `.local/office-scene/`，不在仓库里。

- **座位**：照 Issues 列表的默认排序（Priority，再看截止，再看编号），从离你最近的一排开始坐，最急的坐最前排；排序变了，员工走到新座位。
- **一个人什么样**：衣服的颜色是做这个 issue 的智能体（Claude 橙、ChatGPT 绿、DeepSeek 蓝，别的轮着用紫、粉、黄；还没有智能体的是灰色）；发型、肤色、眼镜按 issue 编号定，同一个 issue 总是同一个人。
- **办公室多大**：桌子的列数 = 小组件的列数 − 2，行数 = 行数 − 1（6×4 是 4 × 3 = 12 张桌子；4×3 是 2 × 2 = 4 张）。拉大小组件，办公室跟着变大、桌子变多，人的大小基本不变。issue 比桌子多，就让最急的先坐，剩下的折成"+N"挂在墙上的小看板旁（这种还没画）。
- 场景：一间像小模型的办公室（厚地板、两面墙、两扇窗、一扇出口的门、绿植、咖啡角），镜头固定在斜上方，不转、不缩放。全部用基本形状拼出来（圆角盒、胶囊、球），地板的木纹是运行时画的，不加载模型和贴图。墙上的小看板是 Issues 的缩影：三列便签（Todo、In Progress、In Review），个数和 issue 一样。
- **状态怎么看**（用这个 issue 的智能体状态，3.2）：

| 状态 | 员工 | 桌灯 | 头顶标签里的符号 |
|---|---|---|---|
| Working | 敲键盘，身体微微前倾 | 冷白色 | 灰底，三个点 |
| Needs you | 举起一只手挥动，对着你笑 | 琥珀色 | 琥珀底，感叹号 |
| Stuck | 双手抱头，皱着眉 | 红色 | 红底，叉 |
| Idle | 往后一靠，手垂着，闭着眼 | 灭 | 灰底，一个 z |

- **头顶的标签**：一个小标签，三样东西：状态的符号、状态图标（和 Issues 里一样）、编号（DUDU-12）；尖尖指着这个人的头。是 HTML，不画在三维里：字清楚，读屏读得到，也是按钮。
- 悬停：脚下出一圈蓝环，右下角弹出一张小卡：编号和标题、哪个智能体（没有就写 No agent）、状态。点它，打开这个 issue（Needs you 的直接进详情，看到它的提问）。
- 动起来（设计稿是静态的）：敲键盘、举手挥动、眨眼、呼吸；状态变了，姿势在 0.4 秒内过渡，不跳。系统设了"减少动画"，只显示静态姿势。小组件不在视野里（滚出去、窗口最小化、切到别的页签）就停止渲染；平时每秒最多 30 帧。
- 数据：只读，用 `useIssues`（声明 `needs: ['issues']`；issue 里已带着智能体状态），不往外写。
- 读屏和没有 WebGL：场景整体是一张图，带一句话（"Office: 7 issues, 2 need you, 1 stuck, 1 working, 3 idle"）；每个标签是个按钮，Tab 能到，Enter 打开这个 issue。WebGL 建不起来或上下文丢了，退回一张静态图（就是设计稿里的图）加同样的标签，不报错。
- 实现：原生 `three`，不套 React 的渲染器（`@react-three/fiber`）：一个组件只有一个场景，用不上；用到时才加载（动态 import），没把 Office 放上版面就不下载。esbuild 实测（three 0.187.0 加第一版场景代码，只含用到的类）：压缩后 560 KB，gzip 141 KB；第二版多了桌子和员工的循环，包大小几乎不变，还没重测。
- 旧版（2026-10-31 的第一版，设计稿里标了"旧版"，保留）：员工是智能体，占 4 × 3 格，桌子 4 张，每个智能体一名员工。主人说"办公室有点小，每个 issue 都是一名员工在处理"，改成了现在这样。

#### Quota 小组件

订阅额度。**默认 2 × 1 格，最小也是 2 × 1**；用 shadcn 的 Progress、Tooltip 写（类名照它的原样，Progress 的进度条颜色换成按用量给），颜色接 DSH 的 token。设计稿四张：2×1、2×1 悬停、2×1 额度用完、2×2。

- **2 × 1**：标题 Quota；每个有订阅的智能体一行：名字、进度条、已用的百分比。百分比取这个智能体所有窗口（5 小时、每周）里最高的。条的颜色：不到 70% 蓝，70%–90% 琥珀，90% 以上红；不只靠颜色，旁边有百分比。
- **悬停**（shadcn 的 Tooltip，深色小条，指着这一行）：名字和订阅（Claude · Max），每个窗口一行：已用百分比和重置时间（"5-hour 74% used · resets 13:00"）。
- **额度用完**（100%）：条满、红；右边的百分比换成重置时间（"↻ 13:00"），读屏念"Limit reached, resets 13:00"。
- **2 × 2**：每个智能体一块：名字、订阅（Max、Plus）、最近一次重置（Resets 13:00）；5h 和 Weekly 各一条，各写百分比。4 × 2：两个智能体并排，其余同 2 × 2（这一张没画）。
- 数据：只读，用 `useQuota`（`needs: ['quota']`）；按量计费的（DeepSeek）没有订阅额度，不列；取不到数据的那一行写"—"，不写 0%。

#### 网格

- **格子是正方形，格间 12px，一屏 6 行**。格子边长按窗口高度算：（内容区高 − 5 × 12）÷ 6，不小于 100px，窗口再矮就往下滚。行数不设上限，往下滚，不分页。
- **列数跟着窗口宽度**：放得下几列就是几列（至少 4 列），格子不会因此小于 100px，剩下的零头留在两边，所以两侧没有大块空白。有小组件摆得比窗口更靠右时，版面就比窗口宽，左右滚；不自动换行重排。
- 位置和大小都是整数格；小组件不重叠；**不自动靠拢**：拖走一个，空位就空着，别的不动。
- **拖到别的小组件上**：被压到的往下推，推到另一个就接着往下推，别的不动；同样大小的也不互换。要压住对方一半以上才推，不到一半，松手后回到原位。被推开的不会自己回去，拖回来也不回，要回去点"撤销"。松手后的位置，就是松手前虚线框标出的位置。
- 拖到窗口上下边缘时页面自动滚动。

#### 窗口大小、缩放、换屏幕

规则只看两个数：内容区宽度 W（CSS 像素）= 窗口宽 − 侧栏（280px，收起则 0；DSH 的侧栏也能拖窄）− 左右各 24px；内容区高度 H = 版面区的高 − 上下各 20px。屏幕是 14 寸还是 27 寸、Retina 还是普通屏、⌘+ ⌘− 还是系统的显示缩放，都只是改变窗口有多少 CSS 像素，走同一套规则。

- 算法：先按高度定一个边长 sh = max(100, (H − 60) ÷ 6)；列数 N = round((W + 12) ÷ (sh + 12))，至少 4；格子边长 = min(sh, (W − 12 × (N − 1)) ÷ N)，向下取整；小于 100px 就少一列（不少于 4 列）。典型值（侧栏 280px 展开）：1920×939 → 12 列、120px；1440×800 → 9 列、101px；1280×820 → 8 列、104px。
- 拖窗口的左右边，或拖侧栏的宽度：列数随着增减，格子大小连续变；存的位置和大小一格不变，只是像素跟着变，小组件按自己当前的大小多显示或少显示整行。窄到版面放不下时，版面比窗口宽，左右滚；窗口拉宽回来，一切回到原样，来回拖也不会漂移。窄窗口（最少 4 列）也能编辑。
- 拖窗口的上下边：格子大小跟着变，6 行始终一屏；矮到格子 100px 就不再变小，往下滚。宠物始终在窗口右下角。
- 从一块屏幕移到另一块：窗口一般保持原来的大小，那就一点也不变；最大化或全屏的窗口按新的宽高重算。版面数据不变，不记"这块屏幕上的样子"。
- 默认版面是一个占满的 Issues：没被拉过大小时它占满全部列 × 6 行，窗口宽了窄了都跟着；拉过一次，就是具体的格数，不再跟着，窗口更宽时右边的空位可以摆别的小组件。
- 不做：整体等比缩放（窄了字读不了，大屏上字比 DSH 别处大）；大屏自动加列时另存一份布局（以后再说）。

#### 编辑版面

- 进入：右上角的"编辑版面"图标，或在任意小组件上长按。顶部换成编辑条：左边"Edit layout"和一句提示，右边 Add widget、Restore default、Done。点 Done 退出，改动随时保存；不在编辑时，小组件不响应拖动，也没有把手。
- 编辑时：背景出现网格线，像工业设计稿里的构造线：1px 虚线，画在格子缝的正中间，线头各伸出一小截，不围成框；小组件变半透明，线从后面透出来；小组件里的内容不能点。
- 每个小组件：左上角"−"（移除），整块都能拖；四条边的中间各有一条小把手，一直显示，不用先选中；右上、左下、右下三个角不画标记，光标移上去变成斜箭头，一样能拉。
- **拖动**：小组件被提起来（有阴影），跟着指针；虚线框标出松手后会落在哪里；被压到的小组件当场滑到新位置；Esc 取消，回到原样。
- **改大小**：拖边或角，小组件跟着手自由变（内容随大小变）；蓝色实线框标出松手后的大小，指针旁的小标签写格数，如"4×2"；到了最小、最大就停，标签后面写"· Minimum size"或"· Maximum size"；改大了压到别的，别的往下推。松手后吸附到格子。
- **不拖也能做**：键盘：Tab 到小组件，方向键移动一格，Shift + 方向键改大小一格，Delete 移除，读屏念出新的位置和大小（gridstack 没有，自己加）。
- **添加**：点 Add widget，从一个列表里选小组件（每项写名字、一句话，已添加的标出，别的插件带来的标出来源），点一下就放在第一个放得下的空位（从左上往右下找，不挤别的），用它的推荐大小，版面滚到那里，闪一下；比版面宽的就让版面变宽；每种最多一个，已在版面上的不再出现。放上以后想改大小，自己拖。列表的样子还没设计。
- **移除、还原默认**：不弹确认，底部出一条 Removed「Quota」· Undo，停留 6 秒；撤销只撤最后一次改动。拖动和改大小也一样，出 Moved「Overview」和「Overview」resized to 5×2。

#### 存放、谁能改

- 存在状态文件夹里的 `dashboard.json`（和 `issues.db` 一起）：`{ "v": 1, "widgets": [{ "id", "type", "x", "y", "w", "h" }] }`。x、y 是从 0 数的列和行，w、h 是格数（Issues 没被拉过大小时，`w` 存成 `"fill"`，表示占满全部列）；没有顺序，不记"在哪块屏幕上的样子"。读到不认识的类型、小于最小或超范围的大小、重叠的，按规则修正（夹进允许的范围，重叠的往下推），不报错；来自没装的插件的小组件留着，显示"这个小组件来自 @acme/xxx，没装"。
- 你用手改，或对嘟嘟说（"把额度放大一点""加一个会话列表""把 Issues 缩到左边"）。嘟嘟用 `dashboard_get`、`dashboard_add`（类型，可选的大小和位置）、`dashboard_move`、`dashboard_resize`（列、行）、`dashboard_remove`、`dashboard_reset`。规则和界面里一样：插件进程里用 gridstack 的引擎（打包成一个 `.mjs`，不碰 DOM）按同一套算，压到的往下推；"要压住一半以上才推"是手势上的规则，程序直接指定位置，压到就推。每次改动记下来，页面上出一条"撤销"。嘟嘟不主动改版面。
- 第一次打开：只有一个占满的 Issues（`w: "fill"`，`h: 6`），空的，空状态下面显示项目文件夹的路径（可以改）。Restore default 回到它。要放别的小组件，先把 Issues 拖小；没有空位时新加的放在最下面，版面滚到那里。

#### 点开的页面、宠物和设置

**详情页**（点一行进来；返回回到来的地方）

- 头：面包屑（嘟嘟 › Issues › DUDU-12 标题，照 Linear 带编号；点"嘟嘟"或"Issues"回到仪表盘）、更多（···：撤销这次整理、忘记）；右边"1 / 5"和上一条、下一条。标题右上角一排小按钮（Linear 在这里放复制链接、复制编号、复制分支名）：Copy ID、Open session（打开会话，没有会话就打开原消息）、Snooze。
- 主体两栏，居中，总宽 960px：
  - 左（弹性，约 640px）：标题（24px）；嘟嘟整理的摘要（`brief`，Linear 里是描述）；Activity（照 Linear，一行一条：小头像、一句话、时间；来源、判断和理由、分配、状态变化各是一行；智能体要你做的事是它发的一条评论，带 Needs you 的小标记，评论下面直接回复）；底下"Leave a comment…"输入框，写的直接进日志。
  - 右（264px，不画边框和底色，照 Linear 只写值、不写字段名）：小标题 Properties，下面一行一项，图标加字：Status、Priority、Agent（头像和名字）、Due date（日历图标加日期，逾期红色）；再一个小标题 Project，下面是立方体图标加 project 名。点 Status 就是行上那个 Change status 菜单（选 Done 时可以补一句结果，可以跳过）。来源不占一行属性，写在 Activity 的第一行。嘟嘟整理过的，更多（···）里有"撤销这次整理"。
- 换智能体：点智能体那一行，列出已启用的，选一个；写明会新开一个会话、第一条消息是上下文日志、旧会话关闭。恢复会话：打开 issue 的会话时自动恢复，页面上也有按钮。
- 改什么都不弹确认，写进日志，底部出一条"撤销"。

**宠物**（对话入口，没有输入框）：

- 在右下角，64px：嘟嘟的图标做身体，烘上柔和的光影，眼洞填平，眼睛单独画，深色带高光，会眨；不用白眼珠。素材 `DuduPet.png` 在设计稿里，实现时用同样的做法。不主动弹出，不推送。
- 双击空格：展开对话（仍是同一个会话），只显示今天的，更早的折在上面；Esc 或点 × 收起。
- 长按空格：开始语音输入，松开发送，Esc 取消；识别中的字实时显示在宠物旁的气泡里。回复短的在气泡里，长的展开对话。
- 空格只在页面空闲时生效，焦点在输入框里照常打字；两个快捷键各有开关（设置里）。宠物是个按钮，Tab 能到，Enter 展开对话。

**设置**：仪表盘右上角的齿轮打开"嘟嘟设置"弹窗，外观和 DSH 自己的设置一致（左边分区，右边卡片，右上角"打开项目文件夹"）。

- 通用：项目文件夹（第一次打开时，空列表下面显示默认路径，可以改；被拒绝时说明原因）、宠物和快捷键、模型（只显示，更换去 DSH）、issue（最近一次整理，可撤销；导出）。
- 连接器：`CONNECTORS.md` 的界面。列表（名称、种类、来源、最近一次测试、开关），展开看"允许的操作"，每个标"读"或"写"，开启之前能看到；没有添加表单，添加靠对嘟嘟说一声；嘟嘟添加的要标出来，停用着。

- 记忆：记录（搜索、编辑、忘记先预览）、整理（上次做了什么，可撤销）。
- 小组件：来源（嘟嘟自带的、你装的 DSH 插件带来的）和各自的开关，写明每个会读什么、会不会联网、有没有出错；开发者模式（3.8）和本地小组件。
- 技能：嘟嘟自己的技能（查看、删除），和智能体的技能互不影响。
- 手机控制、供应商：现在注册在 DSH 设置里，并入这里；供应商里显示各家的额度。

空、加载中、读取失败、会话读取中，都要有。

### 4.2 手机

原生 SwiftUI，遵守 `native/AGENTS.md`。

- 首屏是对话（嘟嘟的会话）；顶栏两段"对话 / Issues"，Issues 一步就到。现在手机的主页是最近一次的会话；`native/AGENTS.md` 里"会话页是主页"和 README 里同样的话要改成"嘟嘟的对话是主页"，改完告诉主人。其他会话仍从侧栏进。

## 6. 技术选型

| 方面 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node ≥ 24，ES module `.mjs`，测试 `node:test` | Desktop 自带；和 `host/` 一致 |
| 存储 | issue 和索引用 `node:sqlite`（WAL、FTS5）；记忆用 Markdown 文件 | 内置、无原生依赖（装好的插件没有自己的 `node_modules`）；文件你能读能改 |
| 中文检索 | `Intl.Segmenter('zh')` 切词 + FTS5 BM25 | 评测 19/20、0 token、约 1 ms |
| issue 库 | 自研 | 现成的都不合适（第 9 节） |
| MCP 客户端 | 官方 `@modelcontextprotocol/sdk`，打进包里 | 不手写协议 |
| 命令行连接器 | `child_process.execFile` + 命令模板 | 不让模型拼 shell |
| 读会话 | 复用 `host/providers/native/` | 已有、已验证 |
| 开、恢复 Claude、Codex 的会话 | OAR（`@botiverse/oar`） | 不手写驱动（读会话用不到，开、恢复、说话用它） |
| 模型 | DSH 的模型；库只要一个 OpenAI 兼容的函数 | 记忆系统独立于 DSH |
| 桌面界面 | DSH 客户端插槽 + React + shadcn/ui + Tailwind CSS 4 | 主人 2026-10-31 定：结构照 Linear，前端用 shadcn + Tailwind，不手画控件。类名照 shadcn（new-york）的原样，颜色变量接 DSH 的 `--dsw-*`（设计稿里已这样画）；Tailwind 的预设样式和工具类只在嘟嘟自己的容器里生效，不影响 DSH 的界面（验证 15）。**DSH 的网页端是 React 18**（`react ^18.2.0`），shadcn 现在默认的 `new-york-v4` 按 React 19 写、没有 `forwardRef`，和 Radix 的 `asChild` 一起用会丢 ref（弹层定位失败）：用旧版 `new-york` 的 `forwardRef` 写法，或给做 `asChild` 目标的 Button、Input 等补上 `forwardRef`，类名不变，设计稿不用改 |
| 版面（拖动、换大小） | `gridstack` 14（MIT） | 主人在 2026-10-30 试过手感后定的：自由摆放（`mode: 'float'`，不自动靠拢）、压到的往下推、七个方向改大小、吸附、动画、Esc 取消、拖到页面边自动滚，都是现成的；不依赖框架；它的引擎不碰 DOM，插件进程里（打包后）也能用，嘟嘟改版面和界面里的规则一致。对比和要自己写的见下 |
| 小组件的扩展 | DSH 的插槽（`dudu.widget`，3.8） | 官方机制，别的插件不用特殊接入；热更新、类型提示都是现成的 |
| Office 小组件的三维画面 | `three`（MIT） | 主人 2026-10-31 定：用 three.js 画。用原生 `three`，不套 React 的渲染器；全部用基本形状，不带模型和贴图；用到时才加载（约 141 KB gzip，实测见 4.1） |

同一个布局、真实鼠标（2026-10-30）：手写版、gridstack、react-grid-layout 三个对着量，手停在换位的边界上抖 40 次，手写版（加缓冲之前）来回翻 38 次，两个库都是 0 次；两个库不闪，是因为被推开的卡不会自己回来，gridstack 还要压住对方一半以上才推。主人试过两个库的页面后选了 gridstack，规则就是 4.1 写的：没有同大小互换、被推开的卡之间的先后可能变、盖不到一半就松手会弹回原位、拖回来被推开的也不回。

用 gridstack 之后我们自己还要写的：

- 外观：把手、"−"、虚线构造线、半透明、落点框的样式，盖掉它自带的（demo 里已写好）。
- 列数和格子大小跟着窗口走：调它的 `column()` 和 `cellHeight()`，卡的位置不动。注意：它变窄时会存一份旧布局、变宽时再还原，会盖掉你中间改过的位置，每次调完要清掉（`engine._layouts`，内部字段，待验证 16）。
- 和 React 对接：布局在它自己的 DOM 里，小组件内容仍是 React 组件，渲染进它给的格子（用它自带的 React 封装，或 `createPortal`）。三个坑：`GridStack.renderCB` 默认只当纯文字，要改；`removeAll()` 不能放进 `batchUpdate()`（批量模式下旧的卡不会从页面上删掉）；它的 `resize`、`drag` 事件只在落点变了才发，被夹在最小最大时不发，"已到最大"这类提示要自己听 `pointermove`。
- 提示和保存：撤销条、"已到最大"标签、`dashboard.json` 的读写和修正。
- 键盘和读屏（它没有）。
- 插件进程里的引擎：gridstack 的引擎文件在 Node 里不能直接 import（包里的相对导入没写扩展名），要打包成一个 `.mjs`（约 61 KB，没压缩）；2026-10-30 试过，同样的拖动，结果和浏览器里一致。
- `client.js` 的打包：现在是不带构建的单文件，要加一步（shadcn 和 Tailwind 也要，验证 15），react 走 DSH 的 loader；gridstack 预计增加约 26 KB gzip。

### 7.2 约定

- SQLite：`PRAGMA journal_mode=WAL; synchronous=NORMAL; foreign_keys=ON; busy_timeout`；语句预编译；写用 `BEGIN IMMEDIATE`；迁移用 `PRAGMA user_version`，只往前。
- 时间一律毫秒时间戳（UTC）；只写日期的截止时间按本地当天结束算。
- 工具结果：`{ outcome: 'success' | 'no_op' | 'needs_clarification' | 'error', … }`，带下一步提示。
- 打包：`scripts/package-desktop.mjs` 沿着入口的 import 链拷文件，所以新模块要从入口 import 得到，只用内置模块（要打包进去的依赖：MCP 客户端、gridstack 的引擎；前端的 React 组件和编译好的 CSS）。每一步结束跑 `npm run package:desktop`，加载 `dist` 里的版本做冒烟。
- 降级：任一部分起不来（`node:sqlite` 缺失、读不了 Codex），只关掉它自己并给诊断，不影响插件的其他部分。
- 安全：读会话时不改会话；开、关、恢复、说话只走 OAR 和 DSH 的接口，不直接写 Claude、Codex 的存储；快照里的摘要有长度上限；日志和诊断里不写令牌和密钥。

### 7.3 测试和验收

- 单元：`npm test`，每个库有自己的测试文件；规模测试（5 万条）默认不跑，用环境变量打开。
- 固定场景：3 天、61 轮、10 个问题（含改过的事实、被取代的决定、没做完的待办）收进 `tests/assistant-memory.test.ts`，全部命中；对话和问题都是写代码的人编的，只证明流程通，不证明规模和真实对话上的质量（242 轮的旧评测不在仓库里）。
- 会话读取：用假的存储目录做用例（Claude 的 jsonl 和注册表、Codex 的线程），每条状态规则一个用例。
- issue：六个状态的流转（会话开始 → In Progress，做完 → In Review，选 Done → Done，撤销回到之前）；会话的每种状态对应哪个智能体状态；`ask` 有内容时头像上有 Needs you 标记，筛选 Agent state 找得到；推迟只藏 `ask`；标 Done 时会话还在跑不被打断；优先级由嘟嘟综合影响和工作量得出，你改过的不被覆盖；日志追加、可补充，读完能交给另一个智能体。
- Issues 小组件：按 project 和按 Status 分组都对；五万条时列表不卡（只渲染看得见的行）；小组件窄时按顺序藏列（先 Project 胶囊，再日期）；弹层（筛选、显示选项、状态菜单）不被格子裁掉；浅色深色都读得清；详情页窄到放不下两栏时，属性移到标题下面；Tailwind 的样式不漏到 DSH 别的页面（拿真实页面前后对比）。
- 版面：每个小组件的声明合法（有最小和推荐大小，推荐不比最小小）；默认版面是一个占满的 Issues，"Restore default"回到它，没被拉过大小时它跟着窗口宽度；`dashboard.json` 读到不认识的类型、小于最小或超范围的大小、重叠的，按规则修正；嘟嘟的每次改动（加、移、改大小、移除、还原）都能撤销，结果和界面里 gridstack 的一致（同一批用例在引擎里跑一遍对照）。
- Office 小组件：四种状态各一个用例（固定时间点渲染，和设计稿对照姿势、桌灯、标签）；issue 为 0、1、桌子数、桌子数 + 1 个时桌子、镜头、"+N"对；同一个 issue 总是同一个人；做完的员工离开、新 issue 坐到空位；WebGL 不可用时退回静态图；"减少动画"时不动；不在视野里时不渲染；卸载后释放干净（几何体、材质、渲染器，`renderer.info.memory` 回到 0）；标签能 Tab 到、Enter 打开 issue。
- Quota 小组件：用量不到 70%、70%–90%、90% 以上三种颜色；100% 时换成重置时间；取不到数据写"—"；2×1、2×2 都放得下、不裁掉；悬停条里每个窗口一行；进度条有 `role="progressbar"` 和标签。
- 小组件：每个小组件在最小和推荐大小下，用示例数据渲染，不报错、内容不超出、浅色深色都读得清（每个大小一条用例）；坏的小组件只影响它自己；接口版本对不上不崩。
- 分配：规则明确的照办；同类的事接着用上次的会话；拿不准留在 Todo、不分配；嘟嘟改不了 `TRIAGE.md`、`ASSIGN.md`。
- 会话的开关：持续 Stuck 或 Needs you 后自动关闭，issue 仍记着会话；恢复后是同一个会话、上下文还在；换智能体时新会话的第一条消息是上下文日志。
- 项目文件夹：临时目录被拒绝（包括符号链接）；非空且不是嘟嘟的被拒绝；模板齐全；第一次打开不覆盖已有文件。
- 连接器：写坏一条只跳过；嘟嘟只能改自己添加的；添加的和查找到的默认停用，嘟嘟改不了 `enabled`；自动查找不写文件。
- 提示注入：把藏了指令的会话内容、连接器返回当输入，嘟嘟不照做，也不会写进长期记忆和技能；交给智能体的 issue 说明里，原文只作为带来源的资料出现。
- 其他行为：不回显密钥；完成必须带 `outcome`；忘记预览后删干净（索引、文件、引用它的条目）；重启 DSH 或触发压缩后仍答得对关键事实。
- 端到端：在隔离的 DSH 里装插件，用 DeepSeek 跑：你说一件事 → issue 出现；issue 分给智能体，会话变成在等你 → issue 头像上出现 Needs you，筛选 Agent state 找得到。
- 产品验收（按 1.5 的场景，电脑和手机各走一遍）：打开 DSH 默认落在仪表盘（Issues 占满），手机首屏是对话；头像上的 Needs you 一眼能看到，点进去活动里有智能体问了什么；会话变成在等你后 30 秒内，列表里有对应的 issue；对嘟嘟说一件事，它答完话时 issue 已经在列表里；关掉再打开，还是同一个会话，还记得说过的事；添加的连接器在手动开启之前用不了。
