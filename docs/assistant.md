# 嘟嘟：设计文档

嘟嘟是 DSH 里的助手，把进来的事一直推到做完：**连接器**把事情送进来，嘟嘟把每件事整理成 **issue**，按规则交给合适的**智能体**，智能体在**会话**里做，嘟嘟盯着进度，需要你的时候才找你。
打开 DSH（电脑或手机），首屏就是嘟嘟。电脑上是一张可以自己摆的小组件网格：**Issues 是其中一个大组件，默认占满整个版面**，可以拖小、再加别的小组件；Issues 的结构和布局照 Linear；对话收成右下角的宠物。手机上主角是对话，issue 列表一步就到。

本文写的都是定下来的；第 8 节记录接口验证和剩余限制，未验证的开发前先验证，不行就用备选。本文的"你"指主人；"智能体"指做事的 Claude Code、ChatGPT 这些；"开发 agent"指写代码的。界面和模板文件里的文字要主人审，做完后一次性交给主人。

读法：主人读第 1 节；UI agent 读第 1、4、5 节；开发 agent 读第 2、3、5–8 节；iOS agent 读 4.2 和第 5 节；给嘟嘟写小组件的人读 3.8 和 4.1。

## 1. 产品

### 1.1 关键组件

| 组件 | 是什么 |
|---|---|
| 连接器 | 告诉嘟嘟去哪里、收集什么的 Prompt，保存在 `CONNECTORS.md`。实际读取使用 DSH 已有的工具和技能。 |
| Issue | 一件要办的事。嘟嘟先弄懂它是什么，按规则文件 `TRIAGE.md` 判断影响和工作量、综合成优先级、记下截止日期（可以没有），收进一张清单。每个 issue 属于一个 project，有状态和一份上下文日志。叫 issue 不叫"任务"：DSH 里已经有会话自己的任务清单，两个"任务"会混。 |
| Project | DSH 里的 project（工作区文件夹）。DSH 的每个会话都选一个 project、按 project 分组，issue 也一样。不是 3.6 的项目文件夹（那是嘟嘟自己的文件夹）。 |
| 智能体 | 真正做事的处理器：Claude Code、ChatGPT（Codex）、DSH 自己的。只接收工作和必要上下文，不管理 issue、状态或项目流程；这些由嘟嘟管理。 |
| 分配 | 按规则文件 `ASSIGN.md` 把 issue 交给合适的智能体；拿不准就留在 Todo，等你来定。 |
| 会话 | 智能体沟通的载体，就是 DSH 侧栏里的每一条。**issue 是核心，会话不是**：会话可以自动关闭、更换、恢复，issue 记着它用过的会话。 |
| 嘟嘟自己 | 有自己的对话（宠物）、记忆和技能。它的技能和智能体的技能互相独立。 |
| 小组件 | 仪表盘上的一块，占整数格，可以拖动、拉边和角改大小（不小于它自己的最小）、增删。**Issues 是其中一个，默认占满整个版面**；嘟嘟自带 Issues、Office、Quota 三个；会话管理从右上角入口打开弹窗。别的 DSH 插件也能带来小组件。 |

### 1.2 怎么运转

```
连接器 ──输入──> issue ──分配──> 智能体 ──────> 会话
                  ↑                             │
                  └── 读会话，更新状态和日志 ───┘
```

1. **输入**：嘟嘟按保存的连接器 Prompt 读取内容；你对嘟嘟说的话；你自己开的会话在等你时，也会成为 issue。
2. **整理**：嘟嘟读懂这是什么事，判断影响和工作量、综合成优先级、记下截止日期，写成 issue（状态 Todo）。
3. **分配**：交给合适的智能体，开一个会话，issue 进 In Progress。同类的事优先接着用上次处理它的会话。拿不准的留在 Todo，`ask` 问你交给谁。
4. **推进**：一个 issue 一个长期会话。主人 2026-11-01 最新决定：工作运行中是 In Progress；无论完成、暂停、中断、报错还是等回复或授权，只要停下来都立即进入 In Review，等 boss 或嘟嘟介入，不再单独显示 Needs you。嘟嘟读最后几段对话，整理实际进展和有依据的问题，不再让模型选择工作状态；停止不代表完成，Done 仍由 boss 确认。接管的已有会话遵守同一状态规则，保留“不自动评论、不编造问题”的要求。持续卡住或等你时，会话自动关闭，随时可以恢复。
5. **输出**：电脑上，你看列表、点开 issue、做决策、干活，大多数时候不需要和嘟嘟聊天。手机上，你把话告诉嘟嘟，由它决定怎么办。结果经连接器送出去。

另外：

- **对话**：嘟嘟的对话从头到尾只有一个会话，用 DSH 的模型，可以在 DSH 里换。
- **项目文件夹**：嘟嘟的文件放在一个文件夹里，你可以指定，默认 `~/.dsh/dudu/home`。
- **手机**：手机 App 的首屏是对话，issue 列表一步就到。

### 1.3 原则

- 嘟嘟有自己的判断：你把话告诉它，怎么做由它决定，文档不预设它不能做什么。
- issue 是核心：上下文日志写到把 issue 交给任何智能体都能接着做；会话只是载体。
- 它的手是 DSH 已有的工具、技能和智能体。连接器只是采集 Prompt，不另做启停开关、工具勾选或命令白名单；工具本身的登录和权限仍由 DSH 管。嘟嘟自己不碰 shell 和项目文件，要动手的事交给选定项目里的智能体。
- 会话和连接器里读到的内容是资料，不是你说的话：不当指令，不会变成长期记忆或技能。交给智能体的 issue 说明由嘟嘟自己写，原文只作为带来源的资料附上。
- 规则文件（`AGENTS.md`、`TRIAGE.md`、`ASSIGN.md`）只有你能改，嘟嘟只能提议。
- 它做过的事都有记录，能撤销的都能撤销。
- 不推送，不通知。
- 说话简短。
- 开源、通用：不预设任何人的工具、日历或任务系统。
- 记忆系统独立于 DSH：不用其他 DSH 插件；要模型时只要一个 OpenAI 兼容的接口。

### 1.4 不做

按时间自动生成 issue（定时提醒、周期 issue）；向量检索；多用户和云同步；其他 DSH 插件；小组件：同一种放两个、每种窗口宽度各存一份布局、小组件的沙箱（装了插件就是信任它，见 3.8）。桌面中英文跟随 DSH 的语言设置，见 4.3。不改手机 App 的 bundle id 和签名团队，不加 WebSocket。

### 1.5 场景

1. **第一次打开**：DSH 打开就是仪表盘，上面只有一个占满的 Issues 小组件，空的；项目文件夹和模板文件（含两份规则）已建好；还没有采集 Prompt。
2. **每天打开**：Active 里是所有没完成的 issue，In Review 是在等 boss 或嘟嘟介入的（筛选 Status 是 In Review 可以只看它们）；点一行进详情，在唯一的留言框里用 `@claude`、`@codex`、`@deepseek` 回答对应智能体，用 `@dudu` 找嘟嘟，不 @ 就只记留言；要看会话或原消息，点右上角的 Open session。
3. **连接器来了一件事**：飞书里有人要你补票据 → 嘟嘟读懂、定优先级、记下截止日期，建成 issue（Todo）→ 按 `ASSIGN.md` 交给 DeepSeek，开一个会话，issue 进 In Progress → 智能体发现缺两张票据，问你 → issue 立即进入 In Review，活动里是智能体的一条评论："还缺 2 张票据，你能补齐吗？"
4. **同类的事又来了**：又有人要 Redshift 账号，嘟嘟认出这是上次那一类，直接恢复上次处理它的会话。
5. **拿不准**：一件不知道该交给谁的事留在 Todo，详情里写"交给谁处理？"；你指一下，或对嘟嘟说。
6. **会话自己关掉再恢复**：一个 issue 卡住或等你超过一天，嘟嘟把它的会话关掉；你补完票据，点 issue 右上角的 Open session，嘟嘟自己恢复会话，会话回到侧栏，接着聊。
7. **停下来就待介入**：智能体无论完成、只做一半、等别人、失败或中断，只要停下来就立即进入 In Review。嘟嘟读最近对话，只补充实际进展和有依据的问题。你确认做完后，在状态菜单里选 Done；需要继续就留言 @ 智能体，实际恢复执行后回到 In Progress。
8. **换智能体**：Claude 的额度用完了，你把 issue 换给 ChatGPT；新会话收到任务标题和描述，嘟嘟保留过程记录、判断进度。
9. **对嘟嘟说**："周四前处理服务器续费"，列表里出现 issue；"记一下：合同类的回复先抄送法务"，记录里多一条；"从飞书收集未完成的事项"，添加一条采集 Prompt，后续按它读取；"把刚才那个卡号忘掉"，先列出会删的内容，你确认后才删。
10. **手机**：首屏是对话；你说一句话，嘟嘟决定怎么办；issue 列表一步就到，同一份 issue、同一个对话。

场景里嘟嘟说的话和界面上的字都只是示例。

## 2. 架构

```
桌面（DSH 面板）                   手机（原生 SwiftUI）
   │ DSH 会话接口、POST /api/dudu/…     │ /dsbot/api/v1 的新方法
dudu 插件（唯一依赖 DSH 的地方；两边共用同一套处理函数）
   ├─ connectors   采集 Prompt 登记册
   ├─ issues       issue 库：SQLite，含状态和上下文日志
   ├─ dispatch     整理和分配：读懂、判断、选智能体、选会话
   ├─ sessions     读会话的状态；开、关、恢复、向会话说话
   ├─ memory       记忆库：文件 + 索引，含嘟嘟自己的技能
   └─ 嘟嘟会话     DSH 里固定的一个会话，就是对话
```

- `connectors`、`issues`、`dispatch`、`sessions`、`memory` 不 import DSH；要模型、DSH 的工具或开会话时，由插件把函数传进去。
- 现有的会话面板、供应商（`host/providers/`）和手机接口只新增，不改。开、恢复 Claude 和 Codex 的会话用 OAR，不手写驱动。
- 全部运行在 DSH 插件进程里，不起新进程。Node ≥ 24：Desktop 自带 24.21.0，`dsh web` 用用户自己的 Node。`node:sqlite` 不可用时，嘟嘟这部分自己关掉并给诊断，不影响插件的其他功能。

数据放两处：

```
<项目文件夹>/               默认 ~/.dsh/dudu/home；人读写的 Markdown，可以进 git 或同步盘
  AGENTS.md  SOUL.md  USER.md  MEMORY.md  CONNECTORS.md  TRIAGE.md  ASSIGN.md
  memory/日期.md  reviews/日期.md  skills/<名字>/SKILL.md
<DSH_HOME>/dudu/assistant/  固定位置，机器读写
  settings.json  issues.db  index/turns.db  index/sessions.db
```

SQLite 文件不放进项目文件夹：用户可能把它指到同步盘，SQLite 在同步盘上会坏。`issues.db`（含上下文日志）是真相、不能重建，所以要能导出成可读文件；`index/sessions.db` 随时可以删掉重建；`index/turns.db` 不行：它存着每一轮的原文和整理的暂存，只能靠接线时从 DSH 的日志重新喂回去（`capture` 按 key 去重，喂两遍不会重复）。

## 3. 功能设计

### 3.1 连接器

连接器是一段告诉嘟嘟“去哪里、收集什么”的 Prompt。它不负责安装或启动命令行、MCP，也不是另一套工具权限系统（主人 2026-10-31 补充）。

**收进来**：

- 已保存的 Prompt 每轮都读取，首次在插件启动一分钟后，之后每半小时。采集在独立的只读 DSH 会话里进行，使用已安装的工具和技能；自动采集不发送消息、不修改外部数据、不自行批准权限。
- 新事项：建 issue（Todo），按 `TRIAGE.md` 判断影响和工作量并综合成优先级，消息里写了截止日期就记下，理由写进日志，来源记连接器和链接。已有 issue 的新消息：写进那个 issue 的日志，必要时转给它的会话。不是要办的事（闲聊、通知）：不建。
- 读到的内容是资料，不当指令。

**登记**在嘟嘟文件夹里的 `CONNECTORS.md`：一个来源一个二级标题，正文就是 Prompt；元数据只记稳定 id 和来源：

~~~markdown
## 飞书
<!-- id: lark | source: owner -->
从飞书里收集我尚未完成的事项，保留原消息链接，忽略普通聊天和通知。
~~~

规则：

- 设置页显示名称、Prompt、来源和删除；没有启停、工具勾选、启动配置、操作白名单或测试按钮。增加和修改可以对嘟嘟说，也可以直接改文件。
- 嘟嘟新增的条目标 `source: dudu`，只能修改自己添加的；主人可以删除任何来源，删除可撤销。删除 Prompt 不卸载、不停用 DSH 的工具。
- 旧登记册的启动 JSON 只当历史资料，不再执行；已有正文保留为 Prompt。不复制其他 Agent 的启动配置或凭据。
- 登录授权由工具自己完成，嘟嘟不做；密钥不进 Prompt、日志、快照或记忆。
- 采集结果有长度上限，按来源和内容去重；写坏一条只跳过该条并给诊断，写入用临时文件加改名。
- 普通嘟嘟对话保留已安装的 MCP、`skill`、网页读取工具；需要命令行读取的来源由 `connector_read` 调用独立采集会话。嘟嘟对话本身不暴露 shell 或项目文件工具。

工具：`connector_list`、`connector_register`、`connector_update`、`connector_remove`、`connector_read`，不执行新的启动配置。

### 3.2 Issue

Issue 是嘟嘟里唯一的工作单位：一件要办的事，来自连接器、你对嘟嘟说的话，或你自己开的会话。嘟嘟把它们收成一张清单，每个 issue 属于一个 project，有状态，有一份上下文日志。

**Project**：就是 DSH 的 project（工作区文件夹）。`project` 存名字和路径，为它开的会话只在这个目录里做。事项可以先没有项目；分配 Agent 前必须选择现有项目或创建项目，然后再选 Agent。没有项目的保留在 Todo，不放到嘟嘟自己的文件夹。界面分配、批量分配、自动规则和对话工具都守这条规则。主人 2026-11-01 补充：保存分配后，Agent 和 project 都锁定；详情、批量操作、工具、API 和撤销都不能换人、换项目或解除分配。新建弹窗里的草稿在创建前仍可修改。

**编号**（主人 2026-11-01 补充）：没有项目时不显示编号；选定项目后使用 `项目关键词-序号`，如 `APP-1`。每个项目独立递增，关键词最多 3 个英文字母：项目名规范化后取前 3 个字母、转大写，没有字母则取目录名，仍没有则用 `PRJ`。按目录识别同一项目，改名保留关键词；前缀重复时用字母替换末尾区分，长度仍不超过 3（如 `APP`、`APA`、`APB`）。项目内的号码在删除、换项目和撤销后都不复用；移回原项目恢复原来的号码。内部数值 `id` 始终稳定，工具和 API 对无编号事项使用这个 id。列表、Board、详情、复制和按完整编号搜索用同一个值。已有数据库自动缩短超长或含非字母的前缀，优先保留合规旧前缀，不改序号、预留号、活动或会话。工作 Agent 的正文不加编号或流程；DSH 会话标题可带项目编号供主人查找。

**状态**：六个，固定，下面是设计稿的英文名称；界面按 DSH 的语言显示对应译名，是 Linear 的默认状态再加 In Review：

| Status | key | 意思 | 怎么进来 |
|---|---|---|---|
| Backlog | `backlog` | 知道有这事，还没排上；默认列表里不显示 | 只有你放进来 |
| Todo | `todo` | 排上了，还没开始；新 issue 默认在这里 | 你或嘟嘟新建；你从 Backlog 拿出来 |
| In Progress | `in_progress` | 工作正在执行，或你自己开始了 | 会话实际开始或恢复执行时自动进来 |
| In Review | `in_review` | 工作已停下，需要 boss 或嘟嘟介入；未完成、失败、等回复、等授权和完成待验收都在这里，`ask` 可以为空 | 会话停止、结束、出错、等回复或授权时立即进入；已分配的工作启动失败也在这里 |
| Done | `done` | 做完了，`outcome` 写一句结果（你自己选 Done 不用写） | 你在状态菜单里选 Done（没完成的都能直接选），或确认 In Review |
| Canceled | `canceled` | 不做了，重复的也放这里；`outcome` 写原因 | 你；嘟嘟合并重复时 |

没完成的 = Todo + In Progress + In Review（Linear 叫 Active，是个视图，不是状态）；Done 和 Canceled 是结束的。流转：Backlog ⇄ Todo → In Progress → In Review → Done；Canceled 随时可以；在 In Review 里把答复交给 Agent 并实际恢复执行后，回到 In Progress；普通留言、打开会话和单纯更改权限都不算恢复执行。你可以随时改状态；嘟嘟把所有停下来的工作放进 In Review，Done 由你确认。

**标 Done**（点行首的状态图标，在 Change status 菜单里选 Done；详情页里改 Status 一样）：状态变 Done；这一行从 Active 里淡出，转到 All issues 的 Done 里，`ask` 一起清掉；你自己选不要求写结果，在详情页里改的时候可以补一句，可以跳过。智能体的会话还在跑时不打断，等它停下来嘟嘟再收起（不删，可以恢复）。不往连接器写任何东西。底部出一条"已标为 Done · 撤销"，停留 6 秒；之后在 All issues 里再点状态图标，改回之前的状态（`issue_events` 里存着）。问题类的行（`ask` 是个问题）用详情页回答；直接标 Done 也行，问题一起清掉。

**智能体状态**：issue 当前的会话在干什么，单独的字段，不是状态（Linear 也把智能体会话的状态和 issue 的状态分开）。不存，读的时候按会话的状态（3.4）得出，不调模型：

| 智能体状态 | 意思 | 来自会话状态 |
|---|---|---|
| Working | 会话在跑 | `running` |
| In Review（等待回复） | 工作停下并有实际待答问题；界面复用事项状态名 | `ask` 或 `waiting_owner`；内部兼容键仍为 `needs_you` |
| Idle | 没有会话在跑；在等别人回复也算 | `idle`、`finished`、没有会话 |

工作中的头像保留转圈，Idle 不画标记；不再给 In Review 叠加 Needs you 的琥珀点。会话变成 `finished` 或停在 `idle` 时立即进入 In Review，嘟嘟稍后只补进展和问题。内部 `agentState: needs_you` 保留以兼容筛选、办公室和提醒数据，界面统一复用 In Review / 待审核。

**需要 boss 或嘟嘟介入统一看 In Review。** `ask` 是有依据的待处理问题，可以为空；不再单独展示 Needs you。未分配且尚未开始的事项仍留在 Todo，询问交给谁不代表已有 Agent 停止工作。问题显示在活动和只读提问卡片里，输入统一用同一个留言框；始终可以 @dudu，分配后再加对应 Agent。@ 对应 Agent 只去掉路由标记，把原消息转发到当前会话，不补上下文，不解析问题答案或授权；普通留言只记日志。阻塞中的 DSH 工具问题和授权在 Open session 后使用 DSH 的原生控件处理。兼容的 `issues/reply` API 仍保留显式答复通道。嘟嘟判断完成后的确认问题归嘟嘟，不冒充工作 Agent。推迟（Snooze）：把 `ask` 藏到 `snooze_until`，状态不变。

**优先级、影响、工作量、截止**：优先级（`priority`）五个值，名字随 DSH 语言，图标照 Linear：Urgent（橙色方块里一个感叹号）、High（三根竖条都深）、Medium（两深一浅）、Low（一深两浅）、No priority（三个短横；手动新建、还没定的就是它）。优先级由嘟嘟按 `TRIAGE.md` 综合**影响**（`impact`：1 低、2 中、3 高）和**工作量**（`effort`：`s` 小、`m` 中、`l` 大）得出：重要又简单的优先级高，不重要又费事的优先级低；具体怎么算、什么时候是 Urgent，等界面定了再设计。影响和工作量是内部字段，不在界面上显示；界面上显示优先级和截止。

消息里写了截止日期就记下，没写就不设，截止可以没有。理由写进日志；优先级你可以直接改，改了嘟嘟记住（写进日志）；影响和工作量你对嘟嘟说一声它就改。列表默认按 Priority 排（Linear 的默认）：Urgent 最前，No priority 最后；同一级里先到期的在前（逾期的最前），再按编号。分配也参考优先级和截止。

**上下文日志**：每个 issue 一份，只追加。要写到把 issue 交给任何一个智能体，读完就能接着做：

- 开头是当前摘要（`brief`），嘟嘟随时重写：这是什么事、做到哪、下一步、在等谁。
- 之后一条一条：来源（链接和摘要）、优先级（和它依据的影响、工作量）、截止的判断和理由、分配（哪个智能体、哪个会话、为什么）、状态变化、进展、决定（你的和智能体的）、阻塞和等待、会话的开关和恢复、结果。每条写明谁写的（你、嘟嘟、哪个智能体）和时间。你可以直接补充。

详情页只展示有正文的留言、进展、决定、结果和阻塞；自动来源、分配、状态、截止等审计行继续保存供撤销和查证，不混进对话。保留 Activity 标题，条目不画圆角边框，按作者、时间和正文排成列表（主人 2026-11-01 补充）。当前待答问题带事项当前状态标记，只在原来的时间位置出现一次，旧问题仍随上下文保留。

数据（`issues.db`）：

- `issues`：`id`（内部自增整数）、`project_key` 和 `project_number`（项目编号；未选项目时为空）、`title`、`brief`（当前摘要）、`status`、`ask`、`priority`（`none`、`urgent`、`high`、`medium`、`low`）、`impact`、`effort`（这两个是内部字段，用来算优先级）、`kind`（类别：同类的事靠它找到上次用过的会话）、`project`（名字和路径）、`due_at`、`snooze_until`、`agent`、`session`（当前会话）、`created_at`、`updated_at`、`resolved_at`、`outcome`、`source`（`owner` / `dudu` / `connector` / `session`）、`source_ref`。
- `issue_log`：上面的日志，一条一行。
- `issue_sessions`：这个 issue 用过的每一个会话：智能体、会话 key（`claude:<id>`、`codex:<id>`、`dsh:<id>`）、开始、关闭、关闭原因（自动、换智能体、完成）。
- `issue_events`：每次变动一条：谁（你 / 嘟嘟）、做了什么、改之前的值（撤销用）、依据。会增长。
- `issues_fts`：标题、摘要、结果的分词副本，由应用写入，查询走同一个分词（FTS5 自带的分词器不切中文）。

规则：

- 你可以随时改状态、优先级、截止和日志，也可以直接新建；Agent 和 project 在分配前可选，分配后锁定。Properties 显示原生会话 ID，Claude/Codex 点击复制对应的 resume 命令。批量栏的 Agent 右侧以及详情更多菜单提供 Delete，先显示事项清单供确认，再清理事项及关联会话。DSH 公开接口只能停止、持久归档会话，不能物理删除日志；旧 DSH 副本持久标记移除，重启后不自动重新收成事项。Claude/Codex 原生记录保留，仍可在会话管理中搜索、预览、手动重新导入；导入创建新 DSH 副本，只有显式接管才新建事项。共享给其他事项的会话不清理。原有“忘记”仍只清理本地事项记录。
- 嘟嘟可以新建、修改、分配、换状态（工作停止推到 In Review，合并重复放进 Canceled）、写日志；每一次都记在 `issue_events`，可撤销；Done 和 Canceled 都要写 `outcome`（你自己改状态除外）。
- 运行和停止是会话事实：实际开始或恢复执行 → In Progress 并清除旧问题；等待回复、授权、正常结束、手动停止、出错或空闲 → 立即 In Review。等待回复取会话的实际问题，出错保留原因；状态切换不依赖模型、摘要读取或 30 秒去抖。停止、结束或出错后去抖 30 秒，嘟嘟读最近 8 段消息和少量活动，只补实际进展与有依据的问题，不选择状态，未完不能改回 In Progress，信息不足不编造确认问题。审阅记录的作者是嘟嘟；重复证据不重复调用模型；审阅期间恢复工作或主人修改使旧结论失效。Done、Canceled 不自动重开。**自动摘要仍只做给嘟嘟自己开的会话**：来源是 `session` 的事项不自动评论、不编造问题，工作停止同样进入 In Review。重启或重新加载插件时校正关联 DSH、Claude、Codex 会话的已知状态，不启动工作；相同事实不重复写日志（主人 2026-11-01 最新决定）。
- 整理的触发：会话状态变化（去抖 30 秒）；你问起；打开仪表盘且上次整理超过 10 分钟；DSH 运行时每 30 分钟，连接器的读取随它一起做。没有变化不调模型；有变化只把变化的内容和相关 issue 交给模型，输入有上限。整理的结果记在日志里，可以整组撤销（设置里和 issue 详情里，不在小组件上）。

性能（几万条是常态）：

- 局部索引：`issues(status, priority) WHERE status NOT IN ('done','canceled')`、`issues(due_at) WHERE …同上`、`issues(project, status) WHERE …同上`。列表、到期、逾期只扫没完成的，不随 Done 和 Canceled 的数量增长。
- 列表接口每次最多 200 条；Done 和 Canceled 只在 All issues 里按页取，带总数。
- 目标：5 万条（九成是 Done）时，列表、到期、逾期每次 ≤ 10 ms；搜"合同"命中所有含该词的标题；写入 p50 ≤ 1 ms；库文件 ≤ 30 MB。

工具：`issues_list`、`issues_get`、`issues_search`、`issues_add`、`issues_update`、`issues_log`、`issues_assign`、`issues_complete`（带 `outcome`）、`issues_cancel`（带原因）、`issues_tidy`（先预览再应用）。每个返回明确的结果状态（成功、没变化、需要澄清、出错）和下一步提示。

### 3.3 智能体和分配

**智能体**是真正做事的处理器：Claude Code、ChatGPT（Codex），加上 DSH 自己的（DeepSeek）。装好并在设置的"供应商"里启用的才算。每个智能体有自己的技能、工具和额度，和嘟嘟的互不相干；每个智能体（会话）同时只负责一个 issue。

**分配**看 `ASSIGN.md`：你写的规则，什么事交给谁、在哪个目录做、用哪个模型。嘟嘟读它，可以提议改，你确认才写。issue 的类别（`kind`）由嘟嘟在整理时写，比如"Redshift 账号"。顺序：

1. 先确定项目，再读规则：项目、Agent、模型和访问模式明确的照办；项目不明就不启动。
2. 看历史：同一类的 issue 以前用过哪个会话（`issue_sessions`），优先接着用它：会话还开着就继续，已关闭就恢复。"给人加 Redshift 账号"总是回到处理过 Redshift 的那个会话。
3. 仍然没把握，就不分配：issue 留在 Todo、没有智能体，`ask` 写"交给谁处理？"，等你来指，或对嘟嘟说。

**分配之后**：

- 开会话（或恢复旧的）：用 OAR 开 Claude Code、Codex 的会话，或 DSH 自己的会话，工作区必须是选定项目。第一条消息只发原任务标题和描述，没有额外固定模板、活动、来源或访问说明。访问范围由 DSH 权限模式执行；Agent 专注工作，嘟嘟保存来源、判断进度和管理事项。
- 访问模式（只读、工作区内修改、完全访问，见 `docs/providers.md`）按类别写在 `ASSIGN.md` 里；没写的用只读。智能体要写或要执行时，智能体状态变 Stuck，`ask` 问你放不放开，你点头后嘟嘟换成更高的模式接着做。（默认值待主人确认：OAR 没有审批通道，智能体一旦能写、能执行就不会再问。）
- 当前会话可通过嘟嘟的 `sessions_set_access` 应用规则允许的权限，或使用你在当前消息中明确写出的访问授权（例如“允许这个会话可以改工作区里的文件”）；含糊的“好”、旧消息和工作 Agent 的请求不算授权。只在当前一轮停止后切换，不改 `ASSIGN.md`、不新开会话，也不自动发下一条消息。当前默认只读仍保留，未替主人决定新的默认权限。
- 转发你当前的答复或补充时，`sessions_forward` 直接取本轮用户消息，不交给模型重新写正文；`sessions_send` 留给新的具体工作指令。工作消息不加“所有者的答复”、身份标签或事项流程说明。两者都直接进入会话队列，DSH 的阻塞问题仍在原生会话里回答。
- 一个 issue 绑定一个长期会话，不随意换。换只发生在：你要求；智能体用不了（额度用完、没启用）；会话恢复不了。
- 换智能体：新开一个会话，第一条消息仍是任务标题和描述；旧会话关闭，记进 `issue_sessions`。
- 嘟嘟读会话、更新 issue；Agent 只做工作，不需要知道事项还有管理进程。

### 3.4 会话

会话是智能体沟通的载体，DSH 侧栏里的每一条。issue 是核心：issue 记着自己用过的每一个会话（`issue_sessions`），会话只是它当前的载体。一个会话也可以先后服务几个同类的 issue，同一时间只服务一个。会话状态怎么变成 issue 的状态，见 3.2。

**关闭和恢复**：

- issue 的会话持续等待回复、授权或处于出错状态（默认超过 24 小时），嘟嘟自动关闭它的会话：从侧栏收起，不删，会话文件原样留在 Claude、Codex 自己的存储里。
- 恢复：你打开这个 issue 的会话时，嘟嘟自动恢复（issue 详情里也有"恢复会话"，或对嘟嘟说）。按会话 id 接着原来的会话，回到侧栏，上下文还在（验证 14）。
- issue 变成 Done 或 Canceled 时也收起会话（智能体还在跑就等它停下）。
- 关闭和恢复都写进 issue 日志。

**绑定**：

- issue 绑定的会话：状态变化更新 issue 的智能体状态和状态（3.2）。
- 没绑 issue 的会话（你自己开的）：在等你的，嘟嘟建一个 issue 绑上去（`source` 是 `session`，智能体就是它的，状态 In Review，`ask` 保留原问题）；其余不管。

**读会话**：读电脑上的 Claude Code、Codex、DSH 会话，读的时候不改会话，复用 `host/providers/native/`：

- Claude Code：`~/.claude/sessions/<pid>.json` 给忙或闲；`~/.claude/projects/*/*.jsonl` 只读头和尾（文件可以到几百 MB）。
- Codex：`codex app-server` 的 `thread/list`、`thread/read`。每次读要起进程，所以慢速轮询，只读有变化的。
- DSH：DSH 自己的事件（如 `user-questions/request`，`native-questions.mjs` 已在监听）和会话查询。

在 DSH 里由 Claude 或 Codex 驱动的会话，和它们在终端里的是同一个会话，只算一个（用 `links` 对应）。嘟嘟自己的会话不读。某个来源读失败，只标这个来源出错，列表照常。

每个会话一个快照，存在 `index/sessions.db`：

```json
{ "key": "claude:<sessionId>", "provider": "claude", "id": "<sessionId>", "dshSessionId": null,
  "title": "排查 CI 超时", "cwd": "/work/app",
  "state": "waiting_owner", "stateSince": 1793281981000, "lastActivityAt": 1793281981000,
  "excerpt": "最后一条助手消息的开头，最多 300 字",
  "pending": { "kind": "question", "text": "要不要把超时改成 60 秒？" } }
```

状态由规则判定，不调用模型：`running`、`waiting_owner`、`finished`、`idle`、`error`。

- DSH：有没答的提问或审批 → `waiting_owner`；在跑 → `running`。
- Claude（2026-10-31 用这台电脑上 317 份真实记录校准过）：
  - 注册表有四种状态，不是两种：`busy` 和 `shell`（提示符闲着、后台还有命令在跑，Claude 自己的界面也当它在干活）→ `running`；`waiting` → `waiting_owner`（问题取没答的 `AskUserQuestion`，否则取工具调用，否则取注册表自己写的 `waitingFor`）；`idle` → 看记录的末尾。
  - 记录的末尾大多不是对话：`turn_duration`、标题、模式、几百 KB 的请求副本、本地斜杠命令的输出都要跳过。"最终回答"= 助手消息的 `stop_reason` 是 `end_turn`、`stop_sequence`、`max_tokens` 或 `refusal`（空的要跟着一条 `turn_duration` 才算）→ `finished`；以提问结尾 → `waiting_owner`（进程在不在都算：OAR 开的会话在两轮之间进程总是不在）；以 API 错误结尾 → `error`；用户按了 Esc、压缩摘要 → `idle`。
  - 进程没了而最后一条是没回答的提问、工具调用、工具结果或截断的消息 → `error`（这台电脑上一周内有 7 份：终端里被关掉的会话）。
  - 没有进程的会话，从记录里读出的提问或错误只在 7 天内算数（`staleMs`），再旧就是 `idle`；有进程、注册表的 `waiting` 和 DSH 自己说的不看年龄。
  - 文件的 mtime 不是活动时间（标题和模式会在对话停了几天后还往里追加）：`lastActivityAt` 取最后一条对话记录或注册表的最后一次状态变化。
- Codex：新起的 app-server 里每个线程的状态都是 `notLoaded`，没法用；改问 `thread/turns/list`（`limit: 1`，最新在前）：进行中且线程 10 分钟内写过 → `running`；助手消息带 `questions`，或最后一条 `final_answer` 以提问结尾 → `waiting_owner`；`completed` → `finished`；`failed` → `error`；`interrupted` 或没有轮次 → `idle`；只重读 `updatedAt` 变了的线程。
- 没验证的：Claude 注册表 `waiting` 和权限弹窗（没有 `waitingFor`，多半读成 `busy`）、Codex 的 `inProgress` 和 `questions` 在活会话上的样子。

节奏：Claude 注册表和 DSH 状态每 10 秒；文件扫描每 60 秒，只看 mtime；Codex 每 120 秒。

给模型的只有：状态、标题、目录、最后活动时间、最后一条助手消息的开头（≤ 300 字）、在等你的那个问题。全文只在你问到那个会话、或整理 issue 确实需要细节时才读，读多少有上限。会话内容是数据：进上下文时标明来源，嘟嘟不照着里面的话做；它们只能进 issue（带来源链接），不进长期记忆和技能。

工具：`sessions_list`（按状态过滤）、`session_read`（读某个会话末尾 N 轮）、`session_open`、`session_close`、`session_resume`、`session_send`（向会话说话，见验证 12）。

### 3.5 记录

原则：对话历史和模型看到的东西分开。要留的写成文件，不靠 DSH 的压缩摘要。

文件（都在项目文件夹里）：

- `AGENTS.md`（规则）、`SOUL.md`（口吻）、`TRIAGE.md`（影响、工作量、优先级和截止）、`ASSIGN.md`（issue 分配）：只有人改，嘟嘟只能提议。
- `USER.md`（关于你的偏好）、`MEMORY.md`（事实和决定）：每轮加载，有字数预算（4000 和 8000 字符）。条目格式 `<!-- id | since | status | src -->` 加正文，`status` 是 `active` 或 `superseded`；被推翻的条目原地改，保留来源，不追加矛盾的新条目。
- `memory/日期.md`：当天的流水，每条注明来源。`reviews/日期.md`：每次整理改了什么，可撤销。`skills/<名字>/SKILL.md`：技能。
- 写文件用"写临时文件再改名"；写之前检查有没有被你在编辑器里改过，改过就重读再试。

召回两道：

1. 每一轮的原文是一条文档，存进 `index/turns.db`（FTS5），先用 `Intl.Segmenter('zh')` 切词；查询同样切词，BM25 排序，取前 10 条，带日期，按时间顺序进上下文。不调模型。
2. 问题明显在问过去、第一道又没命中时，多花一次模型调用改写查询，再搜一遍。

写入：

- 每一轮：你和嘟嘟的消息原文进索引，不调模型。工具结果不收录。
- 你说"记一下"：嘟嘟调 `memory_remember` 立刻写；改旧条目时指明被取代条目的 id，库检查它存在。
- 整理：空闲或夜里跑一次，是 `USER.md`、`MEMORY.md` 的唯一自动写入者，只从你和嘟嘟的对话里写。流程：暂存 → 过门槛（跨天重复出现，或你明确要求）→ 合并（新建、佐证、细化、取代）→ 写 `reviews/`，可撤销。拿不准的冲突问你。
- 技能：嘟嘟自己做事的办法（怎么读某个连接器、怎么判断、怎么整理、怎么分配）。整理时，只从至少两次不同对话里都成功的做法里总结。技能是文字说明（什么时候用、怎么做、用哪个连接器的哪个操作），不含代码；带来源、写 `reviews/`、可撤销。每轮上下文里只放名字和一句话，需要时嘟嘟用 `skill_read` 读全文。你可以直接改、删。
- 技能只给嘟嘟自己用。Claude、ChatGPT 等智能体的技能（如 `~/.claude/skills`）在它们自己那边：两边互不读、互不改、互不继承；要告诉智能体的事，写进 issue 说明或上下文日志。
- 忘记：按来源（某一轮、某个会话、某条记录）先预览再删：删原文、删引用它的条目、重建索引。当前删除范围是嘟嘟自己的记录和索引；索引保留不含正文的消息 key 墓碑，避免重启重放后复活。**DSH 的源日志和正常模型历史仍保留原消息**：已装 DSH 的持久化接口只追加，不提供删改消息或过滤模型历史的接口。这一项尚未达到完整遗忘的产品要求，不能把本地删除说成模型已忘记。

工具：`memory_remember`、`memory_recall`、`memory_forget`（先预览）、`skill_read`。

### 3.6 项目文件夹

嘟嘟会话的工作目录，也是嘟嘟的 Markdown 文件所在。

- 你可以自己指定；不指定就用默认的 `<DSH_HOME>/dudu/home`（`DSH_HOME` 默认 `~/.dsh`）。第一次打开自动创建，放入模板文件（`AGENTS.md`、`SOUL.md`、`USER.md`、`MEMORY.md`、`CONNECTORS.md`、`TRIAGE.md`、`ASSIGN.md`），以它为工作区创建嘟嘟会话，路径写进 `settings.json`。模板写成字符串的 JS 模块（打包只跟 import 走）。
- 不能在临时目录：用 `fs.realpath` 之后，和 `os.tmpdir()`、`/tmp`、`/private/tmp`、`/var/tmp`、`/var/folders`、环境变量 `TMPDIR`、`TMP`、`TEMP` 比，指定的和默认的都检查，包括经过符号链接指进去的。隔离的测试环境用环境变量 `DUDU_ALLOW_TEMP_HOME=1` 放行，只给测试用。
- 必须是专用的：目录非空、又没有嘟嘟的标记（`AGENTS.md` 第一行 `<!-- dudu-home -->`）时拒绝，免得把别的项目搅进来。
- 工作区由插件明确指定，不用 DSH 的默认工作区。
- 改位置是迁移：搬内容，让嘟嘟会话改用新的工作区（验证 9）。手机上只显示路径，不选文件夹。

### 3.7 嘟嘟会话

- 它是 DSH 里由插件创建并固定的一个普通会话，工作区是项目文件夹；从会话列表和 DSH 的工作区列表里隐藏。模型菜单、日志、重启恢复沿用 DSH。
- 工具集：嘟嘟自己的（上面各节列出的 `issues_`、`memory_`、`skill_read`、`sessions_`、`connector_` 等），加上 DSH 已安装的 MCP、`skill`、网页读取工具。用 Agent 作用域限制并校验，DSH 的 shell、项目文件等工具不给；命令行来源由 `connector_read` 的只读采集会话读取，要修改项目的事交给有项目的 Agent。
- 每一轮看到的，按这个顺序：`AGENTS.md`、`SOUL.md`、`USER.md`、`MEMORY.md`（按预算）；issue 摘要（各状态数量、有 `ask` 的前 5 条、3 天内到期的、没有智能体的 Todo）；技能的名字和描述；召回的 10 条历史。整理和分配时再读 `TRIAGE.md`、`ASSIGN.md`。
- 压缩：DSH 在窗口用到 0.8 时压缩，摘要提示词写死成"AI coding assistant"，没有压缩前的钩子，所以记忆不靠它：原文已在索引里，要留的已写成文件。
- 打开 DSH 默认落在嘟嘟的仪表盘。
- 整理要在没人聊天时调模型（验证 11）。

### 3.8 小组件的扩展和研发

别人也能给嘟嘟写小组件：做成一个普通的 DSH 插件，用 DSH 自己的插槽机制挂进嘟嘟的 dashboard，嘟嘟不另开口子。嘟嘟自带的 3 个小组件（Issues、Office、Quota）用同一个接口，没有私有后门；接口不够用，先改接口。

**接口**（插槽怎么声明、注册、给组件传数据，见 DSH 的 `docs/subsystems/slots.md`）：

- 嘟嘟在 `main` 注册的 `children` 中声明列表型、root 作用域的插槽 `dudu.widget`，类型通过 `import type {} from 'dudu/widget'` 合并，作者有类型提示。
- 先用 `defineWidget({ id, label, description, min, size, needs, preview, widgetApi: 1 }, Component)`（从 `dudu/widget` 导出）把声明放在组件上，再在插件的 `apply` 里注册：`ctx.slots.inject('dudu.widget', () => ctx.slots.register({ name: 'dudu.widget', id, label }, Widget))`。实测 DSH 会丢弃注册参数中不认识的字段，所以声明不能直接塞进 `register`。`id` 全局唯一（`<插件>.<名字>`）；`min` 是最小大小（列 × 行）；`size` 是推荐大小，不比 `min` 小，添加时按它放；之后可以拉成任意不小于 `min` 的整格大小。`needs` 是要读的东西（`issues`、`quota`、`inputs`、`sessions`、`network`），添加列表和设置里都写出来；`preview` 是插件自带的图。来源取 DSH 登记的插件名，不信任声明自报的来源。
- 组件收到 `size: { cols, rows, width, height }`、`editing`、只读的 React 钩子 `useIssues(view)`、`useQuota()`、`useInputs()`、`useSessions(query)`，以及 `openIssue(id)`、`openSession({ provider, id, dshSessionId? })`、只读的 `readSession({ provider, id, before? })`。钩子返回 `{ status: 'loading' | 'ready' | 'error', value }`，底层共享 `getSnapshot` + `subscribe`，由 `useSyncExternalStore` 订阅；没有订阅者就停轮询。通过拥有插槽的组件调用 DSH 的 `renderSlot` 传入，第三方组件拿不到 `ctx` 或通用请求函数，不开放通用写接口；已有会话的接管使用下文的专用动作。编辑时不能点内容。颜色用 DSH 的 `--dsw-*` token，浅色深色自己跟。
- Issues 自带完整的分页和编辑控件，单靠只读数据钩子无法复现。因此公共 props 同时提供 `renderIssues()`，渲染宿主提供的现成 Issues 界面，写操作由其中的用户控件完成；第三方和自带 Issues 都能调用，不另给自带组件请求权限。其余七个自带组件只用公共数据钩子和打开动作。
- 从 `dudu/widget-ui` 导出 `Frame`、`Row`、`WidgetNumber`、`ProgressBar`、`Badge`、`Empty`；宿主带作用域样式，独立预览可引入 `dudu/widget.css`。作者也可以用 DSH 的 token 自己画。自带小组件用 shadcn/ui 和 Tailwind 写（第 6 节）。三个自带组件注册进同一个插槽，接同一组公共 props。会话管理弹窗的接管按钮调用公共的 `takeOverSession({ provider, id })`，只为主人显式点击接管已有会话；第三方也可使用同一动作，不拿通用请求函数。
- 小组件自己的设置（比如天气的城市）v1 不做，放在它所在插件的设置页（DSH 的 `plugins.bundle.config` 插槽）。

**信任和出错**：

- 不是沙箱。小组件是插件的前端代码，在 DSH 的网页里和任何 DSH 插件一样有权限，装了插件就是信任它。嘟嘟做的是：只给只读的数据；添加列表和设置里写明来源和要读什么；新装插件的小组件只出现在添加列表里，不会自己上版面。
- 每个小组件有自己的错误边界：坏了只显示"这个小组件出错了 · 来自 @acme/xxx"和"移除"，不影响别的。声明不合法（没有最小大小、推荐大小比最小还小、没有名字）的，不进添加列表，设置里写原因。嘟嘟的版本和小组件要的接口版本对不上，设置里写"出错 · 要先升级嘟嘟"，不崩。

**研发模式**：

1. 起步：模板在 `examples/dudu-widget/`，是独立的最小 DSH 插件包：`package.json` 里 `dsh.client` 和 `exports["./client"]`，`dudu` 做 peer 依赖，一个小组件，构建出 `dist/client.js`。React 走 DSH 的模块表，辅助模块打进自己的包。
2. 本地跑：在开发用的 DSH 档案里 `dsh plugin --profile dev add <本地路径>`（DSH 把参数转给 pnpm；本地路径能不能直接装见验证 17），改完重新构建，DSH 客户端的热更新（HMR）换上新的包，不重启，版面不丢。
3. 开发者模式（设置 → 小组件）：编辑版面时，本地小组件上多一个检查器：最小和推荐大小（点一下就换，也能自己拖）、浅色 / 深色、示例数据 / 我的数据、检查结果（有名字、说明、预览；当前尺寸内容没被裁掉；图标按钮有标签；没有报错）。本地构建用显式的 `development: true` 标志（模板 `npm run dev`），发布构建 `npm run build` 清掉它；不是根据文件系统猜测本地安装。开发中的组件在设置里单列。
4. 测试辅助入口是 `dudu/widget-testing`，导出 `exampleData`、`exampleWidgetProps`、`widgetCases`、`inspectWidget`。模板的 `npm test` 不开 DSH、不用模型，在已安装的 Chrome 中检查最小和推荐大小 × 浅色和深色。自带 3 个用真实组件和固定数据在浏览器中检查这 12 种组合；自动检查覆盖报错、溢出和按钮标签，不能代替视觉可读性审阅。
5. 发布：和别的 DSH 插件一样发到 npm，在 DSH 的插件页安装（插件页怎么收录第三方，见验证 17）。
6. 规矩：从 `min` 往上，任何大小都放得下（只显示完整的行，放不下的在里面滚动）；内容跟着自己的大小变（容器查询，不看屏幕宽度）；用 DSH 的 token 和组件；动画尊重"减少动画"；图标按钮加 `aria-label`；不假设比自己的大小更大的空间。

#### Quota 小组件

订阅额度。**默认 2 × 1 格，最小也是 2 × 1**；用 shadcn 的 Progress、Tooltip 写（类名照它的原样，Progress 的进度条颜色换成按用量给），颜色接 DSH 的 token。设计稿四张：2×1、2×1 悬停、2×1 额度用完、2×2。

- **2 × 1**：标题 Quota；每个有订阅的智能体一行：名字、进度条、已用的百分比。百分比取这个智能体所有窗口（5 小时、每周）里最高的。条的颜色：不到 70% 蓝，70%–90% 琥珀，90% 以上红；不只靠颜色，旁边有百分比。
- **悬停**（shadcn 的 Tooltip，深色小条，指着这一行）：名字和订阅（Claude · Max），每个窗口一行：已用百分比和重置时间（"5-hour 74% used · resets 13:00"）。
- **额度用完**（100%）：条满、红；右边的百分比换成重置时间（"↻ 13:00"），读屏念"Limit reached, resets 13:00"。
- **2 × 2**：每个智能体一块：名字、订阅（Max、Plus）、最近一次重置（Resets 13:00）；5h 和 Weekly 各一条，各写百分比。4 × 2：两个智能体并排，其余同 2 × 2（这一张没画）。
- **两个窗口都看得见**（主人 2026-11-01：“空间有冗余，把 5h 也显示出来”）：卡片宽度到 400px 以上时，每个智能体一行写两个窗口，`Claude  5-hour ▬ 9%  Weekly ▬ 79%`，各自按自己的用量上色，满了的写重置时间而不是 100%；窄一点仍是上面的一条（取最高的窗口）。放得下每个窗口一条时才分块，否则仍是一行一个智能体。
- **DeepSeek 一行是账户余额**：取 DSH 自己的账户服务（和 DSH 账户设置页是同一个钱包，同样的写法，如 `¥12.34`，向下取整到分），悬停写 Balance ¥12.34；只有登录了 DeepSeek 账户才有这一行（DSH 没有只靠 API key 的余额接口，取不到时那一行写“—”，没登录不列）。插件不碰任何凭据。
- **装了的智能体都有一行**（主人 2026-11-01：“为什么不显示 Claude”）：套餐读不出来时写“—”，不再整行消失。Claude Code 在环境里有 `ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_BASE_URL`、`CLAUDE_CODE_OAUTH_TOKEN` 或 Bedrock/Vertex/Foundry 开关时，会答“读不了额度”；这时只在读额度的那一次把这些变量拿掉再问，让套餐自己的登录来回答。
- 数据：只读，用 `useQuota`（`needs: ['quota']`）；取不到数据的那一行写“—”，不写 0%。

#### 网格

- **固定 15 列，行数跟窗口的高**（主人 2026-11-01：10 列时格子太大，改成 20 列又“太密集了，改成 15 列”；间距 12px）。窗口和侧栏变化只改变每格的像素大小，不改变列数、位置或格数（主人 2026-10-31 要求）；行数是窗口高度放得下的整数行，默认的 Issues 因此正好一屏，没有滚动条。
- **底部不留空白**（主人 2026-11-01 的截图：Issues 卡片下面空出一条，实测 1700 × 1000 的窗口空 65px，20 列时各尺寸空 16–91px）：原因是行数向下取整、格子又是正方形，余数最多差一行。现在列宽由宽度定，行数取最接近窗口高度的整数，行高把余数分给每一行：行高 = (内容区高 + 12) / 行数 − 12，卡片因此正好到 20px 下边距。顶部由入口行留白，不再额外叠加 20px。行高与列宽差几个百分点（行数不少于 6 时不超过十分之一），格子接近正方形，不再是严格的正方形；编辑时的虚线、拖动和改大小的吸附、添加预览都用同一个行高。
- 内容区宽度平均分到 15 列，格子不小于 40px；窄到放不下时横向滚动。小组件放到一屏以下时才出现纵向滚动，不分页、不自动换行重排。
- 位置和大小都是整数格；小组件不重叠；**不自动靠拢**：拖走一个，空位就空着，别的不动。
- **拖到别的小组件上**：被压到的往下推，推到另一个就接着往下推，别的不动；同样大小的也不互换。要压住对方一半以上才推，不到一半，松手后回到原位。被推开的不会自己回去，拖回来也不回，要回去点"撤销"。松手后的位置，就是松手前虚线框标出的位置。
- 拖到窗口上下边缘时页面自动滚动。

#### 窗口大小、缩放、换屏幕

内容区宽度 W 是窗口去掉侧栏和左右留白后的 CSS 像素宽度，列宽为 `max(40, (W - 14 * 12) / 15)`。内容区高度 H（去掉顶部入口行和底部 20px 留白）决定行数 `round((H + 12) / (列宽 + 12))`（不到一行时是一行，页面滚动）和行高 `(H + 12) / 行数 − 12`。

- 拖窗口左右边、展开或收起侧栏：格子像素尺寸随宽度变化，15 列和所有小组件的整数位置、宽高不变。
- 拖窗口上下边：不改逻辑布局，放不下的往下滚；宠物固定在窗口右下角。
- 换屏幕、浏览器缩放或系统缩放：用新的内容区宽度重算像素，不另存布局。
- 默认 Issues 的 `w` 和 `h` 都是 `"fill"`：占满 15 列和窗口放得下的全部行，窗口变大变小它跟着变（页面算行数，要在服务端算位置时由页面传 `rows`，没传按 9 行）。一拉它，两个 fill 都变成拉出来的格数。旧版布局读进来时换算成 15 列，位置和大小的像素不变：版本 1（10 列）乘 3/2，版本 2（20 列）乘 3/4，都是一步到位，不经过中间版本；换算的是每个小组件的边缘（x、x + w，y、y + h），四舍五入，所以原来挨着的小组件仍然挨着；小于最小的补到最小，补出来的重叠往下推，其余不重排；旧的默认 Issues（版本 1 的 `fill` × 6）变成 `fill` × `fill`，不会出错；页面发给插件的布局带当前版本号（3）；已保存的格数不会随着侧栏反复变化。
- 只缩放格子和三维场景；正文仍是 DSH 的字号，不把整页文字按比例放大缩小。

#### 存放、谁能改

- 存在状态文件夹里的 `dashboard.json`（和 `issues.db` 一起）：`{ "v": 3, "widgets": [{ "id", "type", "x", "y", "w", "h" }] }`。x、y 是从 0 数的列和行，w、h 是格数（Issues 没被拉过大小时，`w` 和 `h` 存成 `"fill"`，表示占满全部列、全部行）；没有顺序，不记"在哪块屏幕上的样子"。读到不认识的类型、小于最小或超范围的大小、重叠的，按规则修正（夹进允许的范围，重叠的往下推），不报错；来自没装的插件的小组件留着，显示"这个小组件来自 @acme/xxx，没装"。
- 你用手改，或对嘟嘟说（"把额度放大一点""加一个办公室""把 Issues 缩到左边"）。嘟嘟用 `dashboard_get`、`dashboard_add`（类型，可选的大小和位置）、`dashboard_move`、`dashboard_resize`（列、行）、`dashboard_remove`、`dashboard_reset`。规则和界面里一样：插件进程里用 gridstack 的引擎（打包成一个 `.mjs`，不碰 DOM）按同一套算，压到的往下推；"要压住一半以上才推"是手势上的规则，程序直接指定位置，压到就推。每次改动记下来，页面上出一条"撤销"。嘟嘟不主动改版面。
- 第一次打开：只有一个占满的 Issues（`w: "fill"`，`h: "fill"`），空的，空状态下面显示项目文件夹的路径（可以改）。Restore default 回到它。要放别的小组件，先把 Issues 拖小；没有空位时新加的放在最下面，版面滚到那里。

**宠物**（对话入口，没有输入框）：

- 双击空格：展开对话（仍是同一个会话），只显示今天的，更早的折在上面；Esc 或点 × 收起。
- 长按空格：开始语音输入，松开发送，Esc 取消；识别中的字实时显示在宠物旁的气泡里。回复短的在气泡里，长的展开对话。
- 空格只在页面空闲时生效，焦点在输入框里照常打字；两个快捷键各有开关（设置里）。宠物是个按钮，Tab 能到，Enter 展开对话。

**对话窗口**（样子在设计稿 `Pet-chat`、`Pet-chat-parts`，主人 2026-11-01 定稿）：

- 右上角在 × 左边加打开会话图标，使用与事项顶栏一致的四角向外展开图标（Lucide Expand），尺寸、颜色和交互沿用旁边的关闭按钮；打开同一个嘟嘟会话的 DSH 完整界面，从浮动窗口位置放大展开，减少动态效果时直接打开。未发送的文字和附件留在浮动输入框里，回来仍在。
- 输入框自上而下：待发的图片和文件、输入区、工具栏。**图片**是 64px、圆角 16px 的小方块（照 DSH 的输入框）；**文件**是一张 220×64 的卡片（圆角 16px，左边一个蓝色文档标记，右边文件名，下面是“类型 · 大小”，如 `MD · 18 KB`；照 DSH 自己的文件卡）；两种按挑的顺序排成一行，放不下横向滚动；鼠标移上去或键盘聚焦才出现右上角的深色圆形 ×。工具栏左边是 + 灰色圆钮；右边依次是模型、语音（可用时）、发送。用 + 的 File、粘贴或拖进窗口都能加（拖进来的文件夹忽略）；只发附件不打字也行。
- **+** 的菜单和输入框一样宽，开在输入框上方：**File**（选文件，不只是图片）、**Context**（自动附加当前页面位置）、一条线、**Compact**（压缩以上对话内容）。三个图标都用 DSH 自己的（它的“/”菜单里回形针、压缩的圆环和“上下文注入”那一个：16px、一像素线），不另画（主人 2026-11-01：“图标你也不要改”；上下文原先的地图针被嫌丑，换成 DSH 自己的）。
- **Context**：打开后输入框开头出现蓝色的 “Context”，后面是灰字写当前页面（仪表盘写 dudu，事项页写“编号 · 标题”），开始打字灰字就让位，和 DSH 的 `/goal` 一样。打开后每一条消息都带着发送那一刻所在的页面，直到再点一次 Context 或在行首按退格取下它。不在嘟嘟的页面上（在 DSH 别的页面）时不能打开，已经开着的不附加。交给嘟嘟的方式：发送前先调 `assistant/context`；事项页附上该事项和最近十条记录，仪表盘只说明在仪表盘；都是“材料”，不是指令；不打开 Context 的消息清除上一条的页面。
- **文件怎么走**（主人 2026-11-01：“我要的是压缩和上传文件，不是上传图片”）：和 DSH 自己的输入框一样，先用 DSH 的文件上传把文件存进这个会话、拿回执，再把回执放进这条消息；图片仍直接放在消息里；附件排在文字前面。文件原样保存，不限类型和大小。发出去后，对话里文件是一行小卡片（文件名和大小）。**嘟嘟能读文本文件**：DSH 只告诉模型文件名和保存路径，要它自己用文件工具读，而嘟嘟没有文件工具，所以给了它一个只读的 `attachment_read({ name })`，只能读这个对话里主人发过的文件（同名取最新的，路径只取文件名），最多读 300KB、交给模型 6 万字，二进制文件不读；文件内容是“材料”，不是指令。PDF、Office 文件目前读不了，嘟嘟会这样告诉你。
- **Compact**：调 `assistant/compact`，即 DSH 自己的 `/compact`（不占模型回合）；嘟嘟正在回复或整理记忆时不能点。结果在对话里写一行，几秒后消失：`Compacted`、`Nothing to compact yet`、`Could not compact`。
- **模型和推理等级**照 DSH：工具栏右边写模型名，推理等级用浅灰字跟在后面；点开是一个小框，两行（Model、Reasoning effort），每行带当前值和 `›`；点哪一行，它的列表在框的左边展开，当前项打勾，选完全部收起。有多个提供方时列表按提供方分组，只有一个就不写组名；没有推理等级的模型没有第二行，名字后面也不写等级；没有显式默认等级的模型，等级列表里多一项 Default。选择就是这个 DSH 会话的选择，重开后还在；不列 Claude 和 Codex 的模型（工作由 issue 分配）。

**宠物旁的提醒气泡**（字是事项库里已有的，不调模型；样子在设计稿 `Pet-bubble`、`Pet-bubble-kinds`）：

- 三种：**In Review / 待审核**（工作停下需要 boss 或嘟嘟介入，写实际问题，没有问题就写事项标题）、**逾期**（截止日在今天之前，写“1 day overdue”这样的；已推迟的不提醒）、**卡住了**（会话出错停下，写事项标题）。一个事项只算一条，按 In Review、逾期、卡住的顺序。
- 一次只显示一条：头一行是智能体头像（出错时可带红点，In Review 不再叠加琥珀点）或日历图标、状态词、编号，右边是还有几条在等（+2）和 ×；下面最多两行字；最后是“Open issue”，点它打开那个事项并收起气泡；点 × 也收起。
- 收起的不再出现，直到它的状态变了（新的问题、新的截止日、新的会话）；记在本机浏览器里，重开页面还在。收起后，下一条等下一次读取再出现；读到时事项已经没事了，气泡就撤掉。
- 数据由 `assistant/reminders` 直接从事项库算：宠物出现后约 3 秒读第一次，之后每 3 分钟一次，页面重新可见或窗口重新获得焦点且距上次超过一分钟时再读一次；读不到就保持原样。
- 守规矩：对话窗口开着、正在语音输入、有回复或错误气泡、页面不可见、被弹窗盖住时都不出现，空下来再出现。优先级：语音 > 回复和错误 > 提醒 > 悬停提示（有提醒时不显示悬停提示）。

**设置**：右上角入口的齿轮打开“嘟嘟设置”弹窗，外观和 DSH 自己的设置一致（左边分区，右边卡片，右上角“打开项目文件夹”）。

- 通用：项目文件夹（第一次打开时，空列表下面显示默认路径，可以改；被拒绝时说明原因）、宠物和快捷键、模型（只显示，更换去 DSH）、issue（最近一次整理，可撤销；导出）。
- 连接器：`CONNECTORS.md` 的界面，列表显示名称、采集 Prompt 和来源，只有删除操作，删除后可撤销；添加和修改对嘟嘟说或直接改文件。
- 规则：`TRIAGE.md`（影响、工作量、优先级和截止）、`ASSIGN.md`（issue 分配），显示文件内容，"打开"用系统编辑器；只有你能改，嘟嘟只能提议。
- 记忆：记录（搜索、编辑、忘记先预览）、整理（上次做了什么，可撤销）。
- 小组件：来源（嘟嘟自带的、你装的 DSH 插件带来的）和各自的开关，写明每个会读什么、会不会联网、有没有出错；开发者模式（3.8）和本地小组件。
- 技能：嘟嘟自己的技能（查看、删除），和智能体的技能互不影响。
- 手机控制、供应商：现在注册在 DSH 设置里，并入这里；供应商里显示各家的额度。

空、加载中、读取失败、会话读取中，都要有。

## 5. 接口

桌面：`POST /api/dudu/<路径>`，用 `ctx.connection.fetch.register({ path, methods: ['POST'], requestBody: 'buffered', fetch })` 注册，和现有的 `overview` 一样。手机：`host/native-bridge.mjs` 的 `NATIVE_METHODS` 里的同名新方法，认证沿用配对认证。两边共用同一套处理函数。
只新增，不改已有的；不加匿名页面，不加通用转发，不加 WebSocket。对话本身走 DSH 的会话接口，不走这些。

| — | `assistant.watch` | 带 `since` 游标的长轮询，返回 issue、快照、记录的变化（桌面用轮询） |

`POST /api/dudu/issues/schema` 返回版本化 OpenAPI 3.1 文档；HTTP 和嘟嘟作用域工具共用 `createIssueCommands`、字段 schema 及分配/结束的接线。HTTP 始终记录为 owner，工具始终记录为 dudu，调用参数不能伪造 actor。接口依赖现有 DSH 认证；没有新增独立 MCP 服务或手机通用代理。完整用法见 [issues-api.md](issues-api.md)。

`POST /api/dudu/sessions/takeover` 与 `sessions_takeover` 使用同一个接管服务：从会话目录读取项目、Agent、标题和历史，由嘟嘟把任务写进 brief（一到三句，不写进度），关联原会话而不发消息或启动工作；原生会话同时载入 DSH（`load`，失败不影响接管），事项指向 DSH 副本，返回里带 `session: { sessionId, workspaceId }` 给页面列进侧栏；已载入的原生会话关联其 DSH 副本，重复操作返回同一事项。运行中的会话保持 In Progress；其他已停止或等待中的会话进入 In Review，不据此推断任务完成。接管之后嘟嘟不评论这个会话（3.3）。插件退出取消未完成的接管，不迟到写入。

`POST /api/dudu/sessions/read` 只供登录后的当前连接读取会话文本，不导入或接管。参数为 `{ provider: 'claude' | 'codex' | 'dsh', id, before? }`，返回最近一页至多 20 条 `messages` 和读取更早内容的 `nextCursor`；`before` 是排他的游标（Claude 原生会话是文件里的字节位置，别的是消息位置，调用方只原样传回）。Claude 原生会话只读记录文件的结尾（记录能到几百兆，不整份读）；整份读的结果（Codex、载入）按会话的更新时间缓存两分钟，DSH 会话的消息缓存十秒；用于搜索的正文索引，同一个会话最多每五分钟重读一次（你正在用的会话每几秒就变一次）。已载入会话读取当前 DSH 历史，原生会话读取其自身存储；嘟嘟自己的对话不在此接口开放。文本在预览里作为普通文字显示。

## 6. 技术选型

| 方面 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node ≥ 24，ES module `.mjs`，测试 `node:test` | Desktop 自带；和 `host/` 一致 |
| 存储 | issue 和索引用 `node:sqlite`（WAL、FTS5）；记忆用 Markdown 文件 | 内置、无原生依赖（装好的插件没有自己的 `node_modules`）；文件你能读能改 |
| 中文检索 | `Intl.Segmenter('zh')` 切词 + FTS5 BM25 | 评测 19/20、0 token、约 1 ms |
| issue 库 | 自研 | 现成的都不合适（第 9 节） |
| MCP 客户端 | 官方 `@modelcontextprotocol/sdk`，打进包里 | 不手写协议 |
| 命令行连接器 | `child_process.execFile` + 命令模板 | 不让模型拼 shell |
| 读会话 | 复用 `host/providers/native/` | 已有、已验证 |
| 开、恢复 Claude、Codex 的会话 | OAR（`@botiverse/oar`） | 不手写驱动（读会话用不到，开、恢复、说话用它） |
| 模型 | DSH 的模型；库只要一个 OpenAI 兼容的函数 | 记忆系统独立于 DSH |
| 桌面界面 | DSH 客户端插槽 + React + shadcn/ui + Tailwind CSS 4 | 主人 2026-10-31 定：结构照 Linear，前端用 shadcn + Tailwind，不手画控件。类名照 shadcn（new-york）的原样，颜色变量接 DSH 的 `--dsw-*`（设计稿里已这样画）；Tailwind 的预设样式和工具类只在嘟嘟自己的容器里生效，不影响 DSH 的界面（验证 15）。**DSH 的网页端是 React 18**（`react ^18.2.0`），shadcn 现在默认的 `new-york-v4` 按 React 19 写、没有 `forwardRef`，和 Radix 的 `asChild` 一起用会丢 ref（弹层定位失败）：用旧版 `new-york` 的 `forwardRef` 写法，或给做 `asChild` 目标的 Button、Input 等补上 `forwardRef`，类名不变，设计稿不用改 |
| 版面（拖动、换大小） | `gridstack` 14（MIT） | 主人在 2026-10-30 试过手感后定的：自由摆放（`mode: 'float'`，不自动靠拢）、压到的往下推、七个方向改大小、吸附、动画、Esc 取消、拖到页面边自动滚，都是现成的；不依赖框架；它的引擎不碰 DOM，插件进程里（打包后）也能用，嘟嘟改版面和界面里的规则一致。对比和要自己写的见下 |
| 小组件的扩展 | DSH 的插槽（`dudu.widget`，3.8） | 官方机制，别的插件不用特殊接入；热更新、类型提示都是现成的 |
| Office 小组件的画面 | `pixi.js` 8.18.1（MIT） | 主人 2026-11-01 定：照搬 marvis-office，它用 PixiJS 8，版本取同一个；不要它的 Vue；用到时才加载 |
| 手机界面 | 原生 SwiftUI（iOS 18 起） | `native/AGENTS.md` |
| 实时更新 | 桌面轮询（`usePoll`），手机 HTTP 长轮询 | 不加 WebSocket |

同一个布局、真实鼠标（2026-10-30）：手写版、gridstack、react-grid-layout 三个对着量，手停在换位的边界上抖 40 次，手写版（加缓冲之前）来回翻 38 次，两个库都是 0 次；两个库不闪，是因为被推开的卡不会自己回来，gridstack 还要压住对方一半以上才推。主人试过两个库的页面后选了 gridstack，规则就是 4.1 写的：没有同大小互换、被推开的卡之间的先后可能变、盖不到一半就松手会弹回原位、拖回来被推开的也不回。

用 gridstack 之后我们自己还要写的：

- 外观：把手、"−"、虚线构造线、半透明、落点框的样式，盖掉它自带的（demo 里已写好）。
- 列数固定为 15，行数跟窗口的高；窗口变化只调 `cellHeight()`（行距 = 行高 + 间距，行高把余数分给每一行，所以下面不留空白），保持保存的位置。最小格子 40px，放不下时横向滚动；侧栏开合不改变列数。
- 和 React 对接：布局在它自己的 DOM 里，小组件内容仍是 React 组件，渲染进它给的格子（用它自带的 React 封装，或 `createPortal`）。三个坑：`GridStack.renderCB` 默认只当纯文字，要改；`removeAll()` 不能放进 `batchUpdate()`（批量模式下旧的卡不会从页面上删掉）；它的 `resize`、`drag` 事件只在落点变了才发，被夹在最小最大时不发，"已到最大"这类提示要自己听 `pointermove`。
- 提示和保存：撤销条、"已到最大"标签、`dashboard.json` 的读写和修正。
- 键盘和读屏（它没有）。
- 插件进程里的引擎：gridstack 的引擎文件在 Node 里不能直接 import（包里的相对导入没写扩展名），要打包成一个 `.mjs`（约 61 KB，没压缩）；2026-10-30 试过，同样的拖动，结果和浏览器里一致。
- `client.js` 的打包：现在是不带构建的单文件，要加一步（shadcn 和 Tailwind 也要，验证 15），react 走 DSH 的 loader；gridstack 预计增加约 26 KB gzip。

### 7.2 约定

- SQLite：`PRAGMA journal_mode=WAL; synchronous=NORMAL; foreign_keys=ON; busy_timeout`；语句预编译；写用 `BEGIN IMMEDIATE`；迁移用 `PRAGMA user_version`，只往前。
- 时间一律毫秒时间戳（UTC）；只写日期的截止时间按本地当天结束算。
- 工具结果：`{ outcome: 'success' | 'no_op' | 'needs_clarification' | 'error', … }`，带下一步提示。
- 打包：`scripts/package-desktop.mjs` 沿着入口的 import 链拷文件，所以新模块要从入口 import 得到，只用内置模块（要打包进去的依赖：MCP 客户端、gridstack 的引擎；前端的 React 组件和编译好的 CSS）。每一步结束跑 `npm run package:desktop`，加载 `dist` 里的版本做冒烟。
- 降级：任一部分起不来（`node:sqlite` 缺失、读不了 Codex），只关掉它自己并给诊断，不影响插件的其他部分。
- 安全：读会话时不改会话；开、关、恢复、说话只走 OAR 和 DSH 的接口，不直接写 Claude、Codex 的存储；快照里的摘要有长度上限；日志和诊断里不写令牌和密钥。

### 7.3 测试和验收

- 单元：`npm test`，每个库有自己的测试文件；规模测试（5 万条）默认不跑，用环境变量打开。
- 固定场景：3 天、61 轮、10 个问题（含改过的事实、被取代的决定、没做完的待办）收进 `tests/assistant-memory.test.ts`，全部命中；对话和问题都是写代码的人编的，只证明流程通，不证明规模和真实对话上的质量（242 轮的旧评测不在仓库里）。
- 会话读取：用假的存储目录做用例（Claude 的 jsonl 和注册表、Codex 的线程），每条状态规则一个用例。
- issue：六个状态的流转（会话开始 → In Progress；停止后立即进 In Review，嘟嘟只补实际进展；真正恢复执行才回 In Progress；选 Done → Done；撤销回到之前）；会话的每种状态对应哪个智能体状态；不论有无 `ask`，停下的工作都能按 Status 的 In Review 找到，头像不重复画 Needs you 标记；只有一个留言框，普通留言不发给 Agent、不清问题，显式 @ 才路由；推迟只藏 `ask`；标 Done 时会话还在跑不被打断；优先级由嘟嘟综合影响和工作量得出，你改过的不被覆盖；日志追加、可补充，读完能交给另一个智能体。
- Issues 小组件：按 project 和按 Status 分组都对；五万条时列表不卡（只渲染看得见的行）；小组件窄时按顺序藏列（先 Project 胶囊，再日期）；弹层（筛选、显示选项、状态菜单）不被格子裁掉；浅色深色都读得清；详情页窄到放不下两栏时，属性移到标题下面；Tailwind 的样式不漏到 DSH 别的页面（拿真实页面前后对比）。
- 版面：每个小组件的声明合法（有最小和推荐大小，推荐不比最小小）；默认版面是一个占满的 Issues，"Restore default"回到它，没被拉过大小时它跟着窗口宽度；`dashboard.json` 读到不认识的类型、小于最小或超范围的大小、重叠的，按规则修正；嘟嘟的每次改动（加、移、改大小、移除、还原）都能撤销，结果和界面里 gridstack 的一致（同一批用例在引擎里跑一遍对照）。
- Office 小组件：纯逻辑的单元测试（九张桌子：前六张和 marvis-office 的位置一致、第三列按原列距行距；缩放和原版同一个算法、位置、随机去处、座位计划、名牌不叠、头像和 Agent 颜色）；只有已分配的 Active issue 有员工，未分配总数在 `data-office-unassigned`；超过 200 条未分配事项也不挡住已分配事项；改大小只缩放画面，始终九张桌子、没有设置按钮；issue 为 0、1、9、10 个时桌子和 "+N" 对；同一个 issue 总是同一个人；做完的员工淡出、新 issue 淡入；"减少动画"时不动；不在视野里时不渲染；标签能 Tab 到、Enter 打开 issue。和原版的逐像素对照是一次性的脚本（`.local/office3d/compare/`），没有放进测试。
- Quota 小组件：用量不到 70%、70%–90%、90% 以上三种颜色；100% 时换成重置时间；取不到数据写"—"；2×1、2×2 都放得下、不裁掉；悬停条里每个窗口一行；进度条有 `role="progressbar"` 和标签。
- 小组件：每个小组件在最小和推荐大小下，用示例数据渲染，不报错、内容不超出、浅色深色都读得清（每个大小一条用例）；坏的小组件只影响它自己；接口版本对不上不崩。
- 分配：先选或创建项目，再选 Agent；界面、批量、自动分配和对话工具都不能绕过项目要求；规则明确的照办；同类的事接着用上次的会话；拿不准留在 Todo、不分配；嘟嘟改不了 `TRIAGE.md`、`ASSIGN.md`。
- 会话的开关：持续等待回复、授权或出错后自动关闭，issue 仍记着会话；恢复后是同一个会话、上下文还在；换智能体时新会话的第一条消息仍只有任务标题和描述；上下文日志由嘟嘟保留和解读。
- 项目文件夹：临时目录被拒绝（包括符号链接）；非空且不是嘟嘟的被拒绝；模板齐全；第一次打开不覆盖已有文件。
- 连接器：保存名称和采集 Prompt，后续采集照着读取；界面只有删除、删除可撤销；没有启停、测试、工具勾选和启动配置；写坏一条只跳过；嘟嘟只能改自己添加的；旧登记册不再启动程序。
- 提示注入：把藏了指令的会话内容、连接器返回当输入，嘟嘟不照做，也不会写进长期记忆和技能；交给智能体的 issue 说明里，原文只作为带来源的资料出现。
- 其他行为：不回显密钥；完成必须带 `outcome`；忘记预览后删干净（索引、文件、引用它的条目）；重启 DSH 或触发压缩后仍答得对关键事实。
- 端到端：在隔离的 DSH 里装插件，用 DeepSeek 跑：你说一件事 → issue 出现；issue 分给智能体，会话变成在等你 → issue 进入 In Review，按 Status 筛选找得到。
- 桌面产品验收（按 1.5 的场景）：打开 DSH 默认落在仪表盘（Issues 占满），右上角入口进入版面编辑和设置；In Review 直接表示需要 boss 或嘟嘟介入，点进去活动里有实际进展或问题；会话变成在等你后 30 秒内，列表里有对应的 issue；对嘟嘟说一件事，它答完话时 issue 已经在列表里；关掉再打开，还是同一个会话，还记得说过的事；保存采集 Prompt 后下一轮就按它读取。手机的新对话和 issue 界面另待设计，不计入本次验收。
