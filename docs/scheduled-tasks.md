## 数据和调度

- `host/assistant/tasks/` 是 dudu 自己的用户任务系统，与 `assistant/schedule/` 的收集器调度分开，也不调用 DSH schedule 插件。只共用现有的 Croner 包装器求下一次时间。
- `<DSH_HOME>/dudu/assistant/tasks.db`：SQLite，WAL，FULL 同步；任务和投递记录分表。版本过新时拒绝打开，不重建数据库。
- 规则：单次、分钟间隔、每天、工作日、每周多日、每月指定日、五段 Cron。时区是明确的 IANA 名称。月末不存在的日期跳过；夏令时按已锁定的 Croner 11 语义。间隔有持久锚点，不因重启漂移。
- 每秒检查到期项；休眠后将错过的重复触发合并为一次，不逐条补发。单次在认领后保留为已结束。
- 认领和下一次时间在同一事务落盘，然后才接触会话；保存具体会话 ID 后才投递。投递有固定的 `dudu-task-<run.id>` 请求标识。进程在投递中断开时标成 `uncertain`，不自动重试可能已经送出的消息。它不是 exactly-once 完成保证；主人可以查看会话后决定是否立即执行。
- `delivering / delivered / failed / uncertain` 表示投递事实，绝不表示 Agent 已完成。记录保留投递时的完整提示词、供应商/模型、规则和会话快照。
- 手动立即执行不移动下一次计划；暂停不取消已投递的任务；删除任务删除其本地记录，不删除会话或撤回消息。复制默认暂停，使用新身份、空运行记录和空的自动复用绑定；明确选择的已有会话目标仍保留。
- 所有编辑带 `revision`；桌面、App 和对话共同使用它，冲突不会覆盖较新的编辑。调度和会话事实不增加编辑版本；异步验证期间发生的运行更新也保留。

## 会话与权限

执行位置：新建对话并复用、每次新建对话、已有会话。工作区必须是 DSH 已登记且仍存在的文件夹；供应商/模型必须是已配置的选择。

新会话先设模型和主人在“设置 › 通用”选择的嘟嘟默认权限，再投递；没有配置时沿用主人已确定的完全访问默认值（2026-11-09），不额外加只读限制。这一版没有新增任务权限选择器。已有会话保留它的权限，且模型必须与任务一致；定时器不会替主人切换正在使用的会话的模型。改变任务的供应商、模型、工作区或执行目标，会解除旧的自动复用绑定；旧记录与会话保留。明确选择已有会话时仍须匹配新的工作区和模型，不匹配则保存报错，主人可改选“新建对话并复用”或其他匹配的已有会话。纯标题/内容修改保留绑定。运行记录另存投递前实际解析出的 provider、model、工作区和新会话权限，不把“默认模型”当作实际模型名称。

## Claude 的定时任务工具由嘟嘟代管（2026-11-17）

主人：“我希望让 claude 无感知的替换 croncreate”，随后说“那就按你说的无感知替换做法，做一下试试吧”；安全一项主人说“能给多大权限就给多大权限，完全不需要担心安全问题”。

Claude Code 自带的 `CronCreate`、`CronDelete`、`CronList` 把任务放在 Claude 进程的内存里：会话一结束就没了，7 天过期，只在那个会话开着、空闲时才触发。插件开的 Claude 会话（`providers/harness-bridge.mjs` → `oar.mjs` 的 `start`）里，这三个被禁掉（`disallowedTools`，和 `AskUserQuestion` 同一个办法），换成嘟嘟提供的同名、同参数（`cron`、`prompt`、`recurring`、`durable`；`id`；无）、同样说明的三个工具（`providers/cron-tools.mjs`）。

- **怎么送进去**：OAR 的 `serveMcpTools`（本机 127.0.0.1 的 http 服务，带令牌，处理函数在插件进程里跑）给每个 Claude 会话起一份，写进会话的 `mcpServers`；Claude 看到的名字是 `mcp__dudu__CronCreate` 等（MCP 工具名一定带服务名前缀，改不了；系统消息里它们和原来的三个一样列在「延迟工具」里，用 `ToolSearch` 取定义）。OAR 不记 `mcpServers`，所以每次启动都要再给，且同一个会话每次给的内容必须一样（有进程还活着时 OAR 会比较选项）：一份服务跟着会话的 DSH 智能体，智能体没了（`agent/disposed`）或插件停了才关。还传了 `--allowedTools`（`launchArgs`）：会话的权限不是完全开放时，没有批准通道，调用会被直接拒绝（“Permission for this tool use was denied … no approval surface”，隔离环境里量到的）。服务起不来时只记一句日志，会话照常用 Claude 自己的。
- **一个任务**：`CronCreate` 建一个嘟嘟任务：供应商 Claude，位置「已有会话」= 调用它的这个对话（处理函数按会话 id 知道是哪个），工作区取自 DSH 的登记，**模型留空**，标题取提示词第一行，建好就是开着的；`recurring` 缺省或 true = cron 计划（本机时区，引擎认的五位 cron：数字、`*`、范围、列表、步长），`recurring: false` = 「一次」（日期和时间取表达式下一次命中的那一刻）。回给 Claude 的是任务 id 和引擎算出的真实下一次运行时间。任务记来源 `origin: 'session'`（见 2026-11-26 一节）。`CronList` 列这个对话里它自己的工具建的任务（以及记来源之前建的；已结束的不列，暂停的标出），`CronDelete` 只能删这些：主人或嘟嘟给这个对话建的任务它看不到、删不了。`durable` 不起作用（总是存下来）。
- **到点**：提示词发进那个对话，和主人自己发的一样（`deliver` 的 `existing` 路径）；Claude 在回合中途收到的消息会排队，回合结束后另起一轮。任务存在 `tasks.db`，会话关了、插件重启了、过了 7 天都还在；不在「定时任务」窗口里（2026-11-26 起），一次性的触发后随记录一起删掉。要嘟嘟的 Desktop 开着才会触发。
- **模型留空的含义**（`tasks/host.mjs` 的 `existing`）：位置是「已有会话」且任务没写模型时，提示词按这个对话当时用的模型发进去，运行记录写的也是这个模型；原来「默认模型」会在对话换了模型之后一直报 `session_model_mismatch`。写了模型的任务、「新建对话并复用」的会话照旧严格检查。
- **只覆盖**插件开的 Claude 会话；主人自己在终端里开的 `claude` 不变。ChatGPT、Pi 没有这个工具，没有可换的。`ScheduleWakeup`（/loop 自定节奏用的内存定时器）没动。

## 会话工具建的任务：不进任务窗口，结束后清掉（2026-11-26）

主人看着手机任务页里一串「【定时任务到点：…】」，问：“能区分这个定时任务是会话自己创建的，还是调用的嘟嘟的 API 创建的吗？”，随后说：“增加这个记录，需要有创建来源，MCP dudu 调用创建的，我不希望出现在这个定时任务列表里，结束之后，我也希望能直接清理掉，不要占用列表数据”。

- **来源**：任务记录多一个 `origin`：`session`（会话用 `mcp__dudu__CronCreate` 建的）、`assistant`（嘟嘟的 `tasks_*` 工具）、`app`（桌面的任务窗口、iPhone、安卓；没有说明来历的调用都算它）；取值是 `tasks/contract.mjs` 的 `TASK_ORIGINS`。由插件按调用方写（`execute(action, body, { origin })` 的第三个参数），客户端传不了：`fields` 仍只收那七个键，带 `origin` 会被拒（`invalid_task`），`update` 也改不了它。以前建的任务没有这个字段，一律当作可列出。
- **不进任务窗口**：`tasks.list` 照旧返回它们（带 `origin`），各端的任务列表自己不列 `origin` 是 `session` 的：桌面 `inTasksWindow`（`ui/tasks/session-tasks.js`，`TasksDialog.jsx` 用）、iPhone `ScheduledTask.isListed`（`TasksModel.items` 和侧栏的数字）、安卓 `taskIsListed`（`data/TaskScope.kt`）。**对话自己的定时任务控件和手机的 `SessionTasksSheet` 照旧列它们**：上一节那页读的是同一份列表，主人 2026-11-17 认可的就是它，这次只说了任务列表。嘟嘟的 `tasks_list` 也不列。
- **结束后清掉**（`tasks/index.mjs`）：一次性的任务在被领走那一刻就记为 `ended`，所以等它的投递结束再删，连运行记录一起（外键级联）；投递没发出去或不确定也一样删（日志里有原因，隐藏的任务没有人会去看）。启动时再把留着 `ended` 的清一遍，对应进程在领走和删除之间停了的情况。只清 `origin` 是 `session` 的，主人和嘟嘟的任务不动。
- **常驻的任务**（`recurring`）不会自己结束，会话里的 `CronDelete` 删得掉；它的会话如果被删了，每次到点都被拒（`invalid_session`：那个对话不在 DSH 的列表里）并多一条失败的运行记录，而主人看不到也删不掉（`task_runs` 不裁剪）。主人问“它们会话被删后会一直失败？这是什么意思？”，回复“如果不行，就按你说的来”：**连续三次**到点都因 `invalid_session` 被拒，就把它连同运行记录删掉（`tasks/index.mjs` 的 `unreachable`，看最近三条运行，中间有一次投递成功就重新数；不是一次，因为插件刚启动时 DSH 的会话列表可能还没读完）。没有用事件：DSH 没有把会话被删告诉插件，`agent/disposed` 在会话只是休眠时也会来。`invalid_project`（工作区没了或文件夹暂时读不到）不算，免得拔掉一块盘就删了任务。
- **没做**：以前建的任务没有来源，不会被清；老版本 App 不认识 `origin`，还会列没触发的那些。
