# 会话状态重构（2026-11-15）

主人批准：“就用红色实心吧，其他的和你说的一样，开始重构吧”。这一版替代旧智能体状态、完成绿勾、手动状态和 72 小时自动变空闲的逻辑。现有事项工作流始终由主人控制。

| 状态 | 依据 | 头像角标 |
| --- | --- | --- |
| 工作 `processing` | 实际前台轮次正在执行 | 原有中灰旋转圈 |
| 未读 `unread` | 前台已停止，有尚未读到的可见内容 | 静态红色实心点 `#EC1313` |
| 空闲 `idle` | 前台已停止，最新内容已读，或还没有回复 | 原有中灰空心圈 |

优先级为工作、未读、空闲。工作时仍记录已读边界；结束时根据剩余未读决定状态。等待实际提问或授权不算前台正在处理；读过问题只清未读，不代替回答。单独的后台任务也不占用前台状态。

没有会话的事项仍可归入“未分配” `unassigned`，这是事项的关联情况，不是会话的第四种状态。分组、计数、筛选、办公室、侧栏和手机共用 `sessionState`；旧的 `agentState` 和 `agentFinished` 不再发送，手动状态菜单和状态分组拖动移除。待办快捷列表跟随未读分组。分组标题的圆点与头像角标分别显示：标题恢复原有扩散圆点及电脑端颜色选择卡，默认青绿 `#4F948E`；头像未读角标仍为静态红色实心点。电脑端保留已保存的颜色；手机仅随普通 `board.list` 读取电脑选择，不增加色板或实时同步。

## 未读与已读

`host/assistant/sessions/activity-projection.mjs` 注册 DSH 投影 `duduSessionActivity`。2026-11-15 主人进一步明确：Agent 本轮工作完成才更新最后更新时间和未读。助手正文/图片先记录为 pending，只有本轮 `turn/end` 的 `completed`（或 DSH 的 `max-tokens` 正常结束）才发布，采用完成时间；中途持久化消息、工具调用和流式文本不使主页提前上浮。实际阻塞执行的提问/授权仍可提示待答，但不更新消息排序；错误结束仍可产生未读错误，主动停止/中断不把未完成回复当成新完成消息。用户自己发的消息、普通工具输出、日志、用量和压缩事件不单独产生未读。

`assistant/session-reads.db` 是独立持久数据，和可重建的 `assistant/index/sessions.db`、搜索缓存分开。每个会话保存已读事件序号及可选流式文本指纹。序号、轮次、步骤和流式前缀长度单调前进；迟到的电脑或手机请求不能把新消息一并清掉。投影中的新事件先到、对话正文后到时，只确认实际交付并显示的正文坐标。

完成时发布仍使用最后正文的原始 `seq`，不是 `turn/end` 的控制事件序号；否则已经读过的最终内容会再次变未读。版本 3 投影另保留处理进度 `through`、已实际存在的可读内容上界 `readableSeq` 与待完成内容 `pending`：前者防旧冷读覆盖新完成态，后者允许流式/中途消息的精确阅读确认，停止后也不凭空拒绝已交付内容。冷投影缓存会在原生前台结束或结束活动时间变化时失效，即使正文的 `incomingAt` 没变；读请求期间发生的来源变化也不能被标成已经处理。投影由 DSH 按版本重建，持久已读库不重置。本轮 30 条定向检查及编译/打包已通过；实际部署状态见 `docs/mobile-chat-home.md` 的 Lark 修正节，不能将已打包误报为正式 Desktop 已生效。

读到最新内容才确认：

- 桌面：真实会话视口在前景、页面有焦点、未被覆盖、历史加载完成并到达末尾，并且主人在这个会话里点过、滚动过或敲过键，在下一显示帧提交（`session-read-receipts.js` 的 `mayRead`；2026-11-22 主人：“电脑点一下，或者滚动消息，才算已读”，像微信 Mac 版：会话开着、窗口在前也要点一下才算，屏幕上同时开着两个会话时不可能都被读）。内容出现之前 6 秒内到之后的操作都算（正在操作时到的回复算已读）；点一下列表或标签把会话打开的那一下也算（1.5 秒内）；没有操作就一直未读，手机上同样亮红点，等主人在这个会话里动一下。
- 手机：当前电脑/会话/watch 对应，App 在前景、会话未被覆盖或过渡、跟随末尾且最新真实行已渲染可见。流式文本的异步段落准备完成并显示后才确认相应前缀。
- 预加载、retain、搜索、缓存、辅助预览、后台同步以及翻看旧消息均不自动确认。

红点变化立即告诉手机（2026-11-22 主人：红点要像微信一样快，轮询只能保底）：一轮开始或结束、提问或回答被记录、已读或标未读、事项或置顶改变时，插件往声明了 `board.push` 的手机已经挂着的 `events` 连接里放一条很小的 `board.changed`（`host/native-board-changes.mjs`，在 `host/dudu-plugin/index.mjs` 接线，`native-server.mjs` 的 `broadcast` 发送，每个连接只留最新一条，两条之间至少隔 0.4 秒），手机马上重读看板。手机自己的定时只是保底（iPhone 在这条连接上收到过一次推送后改为 30 秒，Android 约 25 秒；没收到过就仍是 5 秒）。电脑页面本来就由 DSH 的会话列表变化推动（`session-activity-updates.js`），5 秒轮询只是保底。

**读记录（2026-11-22，主人：“需要知道是怎么变成已读的，从哪块屏变成已读的都要有日志”）。** 已读回执只留最后一次，也不记是谁读的，所以“两条都完成了却没有红点”事后查不出来。现在每一次真正改动回执的已读、每一次标未读、每一次发布新回答，都在 `~/.dsh/dudu/diagnostics/reads.jsonl`（一个文件 512 KB，满了换成 `.1`，只留本机；`host/read-log.mjs`）里记一行：时间、会话、哪块屏（`desktop` 并带上屏幕上同时有几个会话、这是第几个、是不是内嵌预览；`iphone` / `android` 并带设备 id 的前 8 位；`dudu` 嘟嘟自己的工具；`plugin` 插件自己）、凭什么（电脑：`press` 点击、`wheel` 滚动、`key` 按键、`touch` 触摸、`opened` 点开会话，并带上那个操作是多久前、内容在屏幕上等了多久；手机：`visible` 看着会话末尾、`row` 行上的清除未读或标未读；`tool`；`rebind`）、读到的位置和原来的位置、读的是不是流出来的那一段（`stream`）、读之前和读之后是否未读（`wasUnread`、`nowUnread`）、内容出来多久后被读（`ageMs`）。新回答那一行（`content`）说它发布时是未读（亮红点）还是已经被流出来时看着的屏幕读过了。没有移动任何东西的重复读不记。字段都是短词表和有界数字，不会有提示词、标题、路径或地址。`npm run logs:reads -- [--last 40] [--session <id>] [--json]` 把它排成时间线，标题从事项库只读取得。电脑页面把这些放在 `sessions/mark-read` 的 `source` 里（`session-read-receipts.js`），插件路由用 `cleanReadSource` 清理，并以路由自己知道的为准（来自电脑）；手机的 `session.read` 和看板行操作由连接带出平台和设备。

电脑和手机写入同一服务端记录。接口分别是 DSH 认证路径 `POST /api/dudu/sessions/mark-read` 和手机既有认证 RPC `session.read`；后者还校验当前 `watchId`。`sessions/read` 保留原来的读取会话正文用途，避免路由冲突。请求提交 `{seq, stream?: {turn, step, digest}}`，服务端不替换为请求到达时的最新序号。

启动时并发有界地预热 DSH 会话及事项关联会话的投影，后续复用缓存及正常会话事件；不启动智能体或请求模型。原生 Claude/Codex 索引另保留 `incomingAt`，仅供从未导入的原生会话判定有无未读。导入后的原生 ID 与 DSH ID 统一指向同一日志和已读位置；TUI 新内容经原有同步追加到共享日志后产生未读，不拿轮次完成时间当作另一条消息。冷会话同步在日志成功追加后直接更新这条边界，不为状态轮询反复读取全量历史。后台 Claude shell 保持资源保护，但不充当前台处理。原生历史同步仍只追加；必须替换 DSH 会话 ID 时，仅在旧最后一条已经读过且新最后一条内容相同、没有更晚时间的情况下迁移坐标。

首次迁移没有历史已读凭据：已有可见回复按未读处理，真正打开并读到末尾后清除，不编造旧的阅读记录。旧 `issues.agent_state` 和 `agent_state_basis` 列由事务迁移删除，事项、活动和工作流保留。浏览器保存的分组与筛选迁到新字段，保留明确选择的“不分组”。
